# LuckyEngine and Lux: implementation study

Reviewed October 23, 2026. This replaces the earlier comparison and its withdrawn May-checkout rankings. **Lux is independently developed and deeply inspired by Hazel; it is not a Hazel fork. LuckyEngine is a Hazel fork.** The useful reference is how a problem was solved, under which constraints, and with which remaining weaknesses.

The strongest opportunities found are **mesh conditioning and imported-node correctness; shader reflection and descriptor identity; bounded command/2D submissions; repeatable profiling; and documentation integrated into the editor**. Lux already has substantial systems that the earlier comparison missed. Its retained scene submission, subresource tracking, current audio stack, prefab variants, and rendering validation tools deserve to be evaluated on their own merits. Lucky's robotics and dataset infrastructure solves different product problems. Temporal techniques are documented for future study, not proposed as current work.

### User priorities and comparison rules

Temporal rendering was removed because the prior agent implementation and repeated repair attempts worked badly. It can return later; it is not a priority now. This overrides historical repository text that describes a permanent preference against temporal rendering. Lux's GPU frame slots were Claude's NRI integration choice, not a design the user independently endorsed. They remain open to review against the actual synchronization problem.

Every recommendation should answer: what fails or costs too much; how each implementation works; who owns the data; when it is refreshed; which thread or GPU queue uses it; what is optimized; what is sacrificed; and what evidence would justify changing Lux. A matching dependency or feature name does not answer those questions. Neither an impressive commit message nor an agent's rationale proves a runtime result.

## Rendering implementation comparison

### R1. Overall rendering structure: where Lucky is modernized and where Lux is ahead

The useful comparison is the work required to render a frame, not whether both engines have a class named `SceneRenderer`.

Historical Hazel already gathered per-frame instance batches, ran a depth prepass, tiled light culling, geometry lighting, GTAO, SSR, bloom, and composition, then cleared draw lists. The source at `pr-base:Hazel/src/Hazel/Renderer/SceneRenderer.cpp` establishes that much of the surrounding pass organization is inherited, rather than a wholly new Lucky invention. That baseline also has cascaded shadows and explicit compute-to-fragment barriers. It does not establish Lucky's later NRI, deferred, meshlet, or path-tracing methods.

Current Lucky keeps the inherited CPU gather shape but has replaced important contents. Its raster chain is explicitly ordered in [FlushDrawList](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/SceneRenderer.cpp:5623): shadows -> meshlet cull -> depth -> hierarchical depth -> preintegration -> tiled lighting -> G-buffer -> sky -> GTAO -> deferred lighting -> scene-color preconvolution -> SSR -> forward transparency -> bloom -> composite. Path tracing substitutes a different view pipeline and reuses bloom/composition/selection facilities. This is an imperative pass chain; the existence of `SceneViewPipeline` is not a general dependency-compiled render graph.

Lucky resolves materials during submission, constructs per-instance affine rows, gathers camera and shadow instance lists, uploads, and normally clears maps/vectors after the frame ([SubmitMesh](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/SceneRenderer.cpp:3292), [SubmitStaticMesh](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/SceneRenderer.cpp:3409), [frame cleanup](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/SceneRenderer.cpp:5820)). Its optional offline preservation retains a captured snapshot for repeated samples; that is different from retaining live scene proxies.

Current Lux's [RenderScene](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/RenderScene.h#L83) retains mesh proxies, material rows, and texture slots, compares dense previous sync inputs, and invalidates through scene generations, material revisions, and asset generations. Its [SubmitRenderScene](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/SceneRenderer.cpp#L5858) retains GPU cull groups when their contents remain valid; unchanged covered objects need no per-proxy submission. It still rebuilds some frame buckets and recycles their vector capacity, so “everything persists without CPU work” would also be inaccurate.

**Decision:** keep Lux's retained scene/GPU scene direction. Lucky's clearer separation of raster and path-traced view pipelines is worth studying if Lux adds a second renderer. Replacing Lux's retained path with Lucky's per-frame material resolution and draw reconstruction would risk losing an optimization Lux already implements. Compare CPU sync/submission timings and asset-edit invalidation correctness before reorganizing ownership.

### R2. NRI integration and frame slots: the same basic solution, different ownership

**Problem.** The application can acquire swapchain images in an order different from CPU frame production. Reusing an upload buffer, allocator, descriptor set, or timer slot before the GPU finishes consumes partially overwritten data. A frame count by itself does not prove completion.

Lucky's [NRIDevice](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/RHI/NRIDevice.h:20) wraps Vulkan objects created by its device manager. It obtains NRI Core, Helper, SwapChain, WrapperVK, optional RayTracing/MeshShader, and upscaler interfaces. Optional broad shader-stage masks are filtered by supported capabilities. This is a Vulkan-backed NRI implementation, not proof that every nominal DX11/DX12 platform stub is a working equal backend.

The actual [BeginFrame](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Platform/Vulkan/VulkanSwapChain.cpp:568) computes `currentFrameIndex = frameCounter % framesInFlight`. Before reuse it waits for the corresponding timeline value, checks the observed value, resolves completion callbacks, drains completed destruction buckets, acquires an image, and resets the slot's command allocator. The acquired image index is kept separately. [Present](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Platform/Vulkan/VulkanSwapChain.cpp:658) waits on the acquire semaphore indexed by frame slot, signals a release semaphore indexed by acquired image, and signals the monotonic frame timeline. Counter advancement occurs after a successful submission path. Failed recording/submission asks for recreation and fails callbacks.

This is important context for Lux: Lucky does **not** demonstrate an alternative in which swapchain-image indexing replaces frame slots. It uses the same broad idea as Lux's monotonic render frame and completion-gated slots. Lux's [RHIDevice](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/RHI/RHIDevice.h#L72) also imports a preexisting Vulkan device, with explicit destruction ordering. Lux's [RenderCommandBuffer](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/RenderCommandBuffer.h#L61) owns NRI recording/submission, pooled command buffers, queue timeline values, completion waits, and acquire-semaphore consumption by the backbuffer consumer.

**Tradeoff.** Lucky's shared command buffer minimizes ordinary frame submissions; the dedicated/offscreen `RenderCommandBuffer` path creates a one-shot allocator/buffer, submits on graphics, and calls `QueueWaitIdle` ([RT_Submit](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/RenderCommandBuffer.cpp:341)). This path is simple and synchronous but can stall unrelated graphics work and repeats native allocation. It is not a claim that every recording/capture path waits the queue idle: specialized FFmpeg recording workers have their own per-slot/fence NRI resources. Its [RendererTransferQueue](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/RendererTransferQueue.h:10) is an MPSC queue drained in an idle renderer window; “transfer” here does not establish asynchronous use of a dedicated GPU transfer queue. LuckyEditor currently selects `SingleThreaded` execution ([application specification](M:/LuckyEngine/MAC-Source/LuckyEditor/src/LuckyEditor.cpp:509)); renderer-side/RT naming alone does not prove ordinary editor frames execute on a separate render thread. Current Lux Windows does use a render thread, so CPU concurrency and lock-cost comparisons must preserve that difference.

**Decision:** review Lux's implementation against these invariants rather than declaring either agent's NRI migration correct by pedigree. Keep separate image/slot identity and real completion. Compare failure callbacks, acquire/recreate paths, and teardown. Adapt specific robustness gaps; do not replace Lux's command pool with Lucky's per-operation create/wait/destroy path without evidence. Test nonsequential MAILBOX acquisition, resize/minimize, failed submit, offscreen capture, and shutdown with streaming resources.

### R3. GPU lifetime: generation pinning is more valuable than arbitrary delays

**Problem.** A `Texture2D` or `MeshSource` can remain the same CPU object while its native resources change. A reference to the object is insufficient if the GPU command requires yesterday's image, buffers, or acceleration structure.

Lucky's [FenceDeletionQueue](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/FenceDeletionQueue.h:17) has open/closed buckets keyed by `(fence, expectedValue)`. Deleters without a known submission wait in a pending list. Under the graphics queue lock the next submit attaches them; success closes the bucket, failure returns it to pending. `Drain` checks actual fence progress and executes callbacks outside the queue-map mutex, while serializing native destruction with the device resource mutex ([implementation](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/FenceDeletionQueue.cpp:12)). Forced drains explicitly require a previously idled queue/device. Thus the important property is not “delete after three frames”; it is connection to a submission whose completion has been established.

Its [bindless table](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/BindlessResourceManager.cpp:228) registers an exact texture descriptor lease and returns an opaque generation pin. PT gathered-frame ownership retains that generation. A replaced/expired texture generation can be reclaimed only after consumer pins disappear and fence retirement completes ([CollectUnusedTextures](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/BindlessResourceManager.cpp:337)). Buffer categories use corresponding retained native-buffer ownership and delayed slot reuse. Completion is published atomically to avoid inverting table/resource lock order ([RetireAfterSubmission](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/BindlessResourceManager.cpp:297)). Limits are fixed at 1,024 buffers per category and 1,024 textures; registration can fail, so every caller needs a fallback.

The meshlet bounds arena is similarly versioned: if an asset expires or changes GPU generation, registrations repack at a frame boundary; a dirty arena publishes a new immutable GPU buffer, retained through the consuming command buffer's completion. It does not overwrite an old arena even if byte size is unchanged. Allocation/upload failure clears culling metadata and renders full meshlets, then retries ([MeshletCullPass](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/SceneRenderer.cpp:4058)).

The same-generation rule reaches PT: a BLAS captures its vertex/index buffer references and offsets. `AddInstance` reads those captured values, not mutable live `MeshSource` buffers ([PathTracerScene](M:/LuckyEngine/MAC-Source/Modules/Hazel.PathTracing/src/Hazel/Renderer/PathTracing/PathTracerScene.cpp:335)). Mixing an old BLAS's primitive range with freshly rebuilt mesh buffers can cause invalid hit-shader access even though both objects look valid individually.

**History.** The broad hardening commit `097d8bf42` touches bindless retirement, resource leases, meshlet arena generations, uploads, unsupported devices, and frame failure handling. Its size matters: the renderer's current safety model is the result of multiple repairs, not a property of merely choosing NRI. The code and architecture also record previous descriptor-ordering/device-loss failures.

**Decision:** high-value audit pattern for Lux: record the exact resource generation each queued draw/dispatch owns; test native resource replacement with frames in flight; associate descriptor-slot recycling with real completion. Lux already has generation/revision mechanisms and frame-tagged deletion, so first compare its actual descriptor-group, texture replacement, and upload paths. Do not add a parallel retirement system before locating the gap. A useful stress scene repeatedly reloads geometry/material textures, toggles render modes, deletes entities, and resizes, with GPU validation and descriptor pressure enabled.

### R4. Resource states: Lucky's simplicity has limits; Lux should preserve its stronger model

Lucky tracks canonical access/layout/stage in [ImageInfo](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/Image.h:116); views can point at a canonical owner. [TransitionImage](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/Renderer.cpp:949) compares all three fields, records a whole-image barrier, then updates state. Comparing stage too repairs dependencies when access/layout match but execution stage changes. Descriptor-bound images are scanned in two passes, sampled images first and storage images last. Manual-barrier passes bypass that scan. Explicit buffer barriers handle compute -> indirect and compute -> graphics handoffs.

This is not a full dependency model. Several draw paths transition material images only while the render pass is pending, before its first draw ([example](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/Renderer.cpp:2314)). `TransitionImage` skips an identical state, so same-state UAV write/read dependencies require explicit ordering elsewhere; FFT bloom explicitly supplies such barriers. Whole-image state does not independently represent one mip read while another is written. These observations identify constraints, not proof of a reproduced failure in all current content.

Lux's current [ResourceStateTracker](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/RHI/ResourceStateTracker.h#L58) is per command buffer, tracks partial subresource ranges, counts UAV -> UAV as a barrier, returns resources to declared resting states at `End`, and can log requirements for render-graph checks. [RenderCommandBuffer](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/RenderCommandBuffer.h#L77) requires descriptor/buffer states as bindings change, closes rendering when necessary, and reopens with loaded attachments.

**Tradeoffs.** Lux's stronger bookkeeping costs CPU work and potentially redundant return-to-resting-state barriers. Returning to a state does not replace a cross-queue wait; overlapping use must still be synchronized. Lucky's global canonical state is smaller/simpler under serialized recording and one graphics queue, but is harder to extend safely to parallel recording or independently synchronized queues.

**Decision:** keep Lux's explicit subresource/requirement design unless measurements expose an actionable cost. Borrow Lucky's evidence-driven tests for stage changes and exact generation ownership. Audit barrier counts and unnecessary resting-state round trips rather than weakening the model wholesale. Distinguish frame lifetime, execution ordering, resource state, and host synchronization; each solves a different part of the problem.

### R5. Reflection and bindless descriptor ordering: a small mapping error caused device loss

**Problem.** Shader binding numbers and NRI descriptor-range indices are different. NRI updates a range by its position in the pipeline layout; an unordered reflection map does not guarantee that binding zero is range zero.

[Shader.cpp](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/Shader.cpp:329) documents and implements canonical sorting by `baseRegisterIndex`. Before that repair, a PT layout reflected set 4 in an order such as `t1,t2,t3,t0,t4,s5`, while the bindless writer assumed vertex buffers lived at range zero. The vertex array remained null and the wrong buffer category received writes. The reported result was a GPU null-address access/device loss that looked like an asset-streaming problem. `DescriptorSetManager` independently constructs the same canonical binding-to-range map ([line 825](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Platform/Vulkan/DescriptorSetManager.cpp:825)).

A second repair removed a global cross-shader `(set,binding)` -> UBO/SSBO-name cache. Different shaders legitimately reused binding numbers with different block names; the global cache let compilation order decide names. Reflection now belongs to each shader, with only its own cross-stage declarations merged. [Architecture notes](M:/LuckyEngine/MAC-Source/.claude/docs/Architecture-LuckyEngine.md:202) explain the failure. Some [MeshletCull shader comments](M:/LuckyEngine/MAC-Source/LuckyEditor/Resources/Shaders/Meshlets/MeshletCull.hlsl:25) still claim the old global registry exists. Source implementation supersedes those comments.

**Decision:** audit Lux's binding-to-range translation and cross-shader binding policy with direct layout tests; do not infer safety from successful shader compilation. Lux currently has a shared global shader binding namespace, so removing it would be an architecture change, not a safe one-line transplant. Check whether its implementation uses that namespace deliberately or still has the accidental cross-shader name aliasing Lucky removed. A focused test reflects two shaders in opposite orders, with distinct names on the same legal binding, and verifies native descriptors point to intended resources. Shared bindless sets also need identical layout contracts across every consuming pipeline.

### R6. Visibility, meshlets, and LOD: materially different algorithms

Lucky uses two levels of raster culling. Static imported instances first get CPU world-sphere/frustum filtering. Shadow lists are built independently, so offscreen casters can remain. PT disables camera-frustum filtering because reflection/GI/shadow rays require offscreen geometry ([SubmitStaticMesh](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/SceneRenderer.cpp:3449)). Animated `SubmitMesh` does not mirror the same main-view CPU sphere filtering in the inspected function; do not generalize the static path to all meshes.

Lucky's meshlet raster path is **off by default**, device gated, and currently disabled while raster DLSS is active because meshlet shaders do not emit the required motion vectors ([options](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/SceneRenderer.h:74), [cull guard](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/SceneRenderer.cpp:4064)). It is an optional execution route, not the engine-wide default GPU-driven renderer.

When enabled, [MeshletCull.hlsl](M:/LuckyEngine/MAC-Source/LuckyEditor/Resources/Shaders/Meshlets/MeshletCull.hlsl:1) runs a 64-thread compute group over `(meshlet, instance)` pairs, transforms the sphere, tests six frustum planes and a quantized meshoptimizer backface cone, atomically appends survivors to a per-draw `uint2` visible list, and increments that draw's mesh-task indirect X count. A clear dispatch initializes arguments to `{0,1,1}`. Both meshlet depth and meshlet G-buffer passes consume the **same** visible list, LOD, and position transform. Compute -> indirect and compute -> graphics barriers provide the handoff. Readback statistics lag by frames in flight instead of stalling to obtain the current count ([C++ dispatch/ordering](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/SceneRenderer.cpp:4183)).

LOD is selected on CPU per draw, using simplification error projected to pixels. The highest projected error across the draw's instances wins, so one near instance can keep every instance in that batch at high detail ([selection](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/SceneRenderer.cpp:4026), [metric](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/SceneRenderer.cpp:3488)). This reduces management complexity but spends extra triangles on distant instances. Culling still records one compute dispatch per draw and allocates visible-list capacity for all candidate pairs. No HZB occlusion test appears in this meshlet shader; the renderer's HZB serves other effects and must not be advertised as meshlet occlusion automatically.

Current Lux instead has a [task-shader depth path](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Editor/Resources/Shaders/PreDepth_Meshlet.glsl): a task workgroup handles up to 32 meshlets for one instance, writes surviving IDs into a small payload, and emits mesh workgroups immediately. It does not build Lucky's external visible-list/indirect buffer. The G-buffer remains the classic route in the inspected SceneRenderer. Importantly, Lux explicitly disables its cone test because winding/Y-flip/mirrored transforms previously rejected visible geometry. Its meshlet prepass currently disables retained GPU cull groups ([predicate](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/SceneRenderer.cpp#L6589)); enabling one optimization can therefore remove another. Classic GPU groups select per-instance LOD outputs separately.

**Correctness questions before adapting Lucky.** Its cone transform assumes near-uniform scale, and its comment asserts errors only keep extra clusters. That is not a mathematical proof under arbitrary nonuniform/mirrored transforms. The shader uses the maximum **row** norm for sphere radius; for a rotated nonuniform TRS transform, maximum row norm need not equal the largest singular value and can underestimate it. For example, scale `(2,1,1)` followed by a 45-degree Z rotation has maximum row norm `sqrt(2.5) ~= 1.581`, while its maximum stretch is `2`; a unit sphere requires radius `2`. This is a mathematical weakness/review hypothesis, not a reproduced scene bug. Lux uses maximum basis-vector length, conservative for pure TRS but also not a universal shear bound. Lucky's cull input does not carry a two-sided-material flag. Validate two-sided foliage, negative scale, nonuniform rotated children, sheared hierarchy transforms, near-plane crossings, and mirrored winding before enabling cone culling broadly.

**Decision:** Lucky's shared meshlet list for depth+G-buffer is a strong design candidate if Lux's measured cost is repeated geometry processing. Lux's task path avoids the external list, extra clear dispatch, global atomics, and memory traffic; it may be better for smaller scenes. First benchmark classic retained GPU groups, Lux task depth, and an isolated shared-list prototype on identical content/hardware. Preserve Lux's alpha-test/depth-equality fixes and robust fallback. Do not reenable the cone simply because Lucky has it.

### R7. Light assignment: tiled depth ranges versus 3D clustered lists

Lucky's [LightCulling.glsl](M:/LuckyEngine/MAC-Source/LuckyEditor/Resources/Shaders/LightCulling.glsl:1) uses 16x16 pixel workgroups. Threads reduce opaque depth to a tile min/max, form the tile volume, cooperatively test lights, accumulate shared point/spot lists, and write 16-bit indices. One packed header stores point and spot counts. The **combined** output cap is 64: point entries consume capacity first and spots get the remainder. The method has bounded memory/output cost, but many overlapping lights can be omitted and point-light priority can starve spots.

Transparency needs a second grid. A transparent fragment can lie in front of all opaque surfaces, so reusing the opaque tile's minimum depth removes lights that should reach glass. Lucky sets minimum depth to zero for its transparent dispatch while retaining the opaque far bound ([line 114](M:/LuckyEngine/MAC-Source/LuckyEditor/Resources/Shaders/LightCulling.glsl:114)). This fixes tile-shaped dark patches at a cost of extra dispatch/storage and larger light lists for transparent regions. The point-light test inflates radius by 30%; spotlights use an approximate enlarged sphere rather than an exact cone test. Conservative slack trades extra shading for fewer missed lights.

Lux's current [ClusterLightCulling](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Editor/Resources/Shaders/ClusterLightCulling.glsl) dispatches one invocation per 3D froxel and tests view-space sphere/AABB overlap. Separate point/spot global lists are dynamically packed with atomic cursors; there is no fixed 64-light local cap. There **are** global capacity limits: offset/capacity calculations truncate writes safely when full, so “unlimited lights” would be false. It also clamps source light counts to 1,000 point and 1,024 spot. Each invocation scans lights twice—count and write—and transforms positions in both loops. This is a concrete GPU cost to profile, not a reason to declare clustered shading inherently superior.

Lux cluster construction/assignment is depth independent, so transparency shares its spatial partition and the work can run before the depth prepass. Current source has an optional async-compute path ordered with an explicit queue wait rather than a render-graph cross-queue edge ([graph contract](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/SceneRenderer.cpp#L4242)); existence of the option does not establish that it is enabled or profitable by default.

**Decision:** keep Lux's clustered architecture as the working baseline. Learn from Lucky's cooperative per-group light evaluation, 16-bit bandwidth reduction, explicit capacity policy, and transparent-volume reasoning. Candidate Lux experiments: pretransform lights once, distribute cluster tests across lanes, evaluate 16-bit IDs within known bounds, and report global overflow visibly. Measure sparse scenes, many overlapping lights, depth discontinuities, glass in front of opaque geometry, and compute/graphics contention. A tile renderer can win on some hardware; choose with timing and missing-light tests, not feature names.

### R8. Deferred lighting and G-buffer: shader resource pressure can dominate

Lucky packs albedo/emission into sRGB RGBA8, normals into octahedral RG16F, and metalness/roughness into RGBA8, reconstructing position from depth ([shared decode/bindings](M:/LuckyEngine/MAC-Source/LuckyEditor/Resources/Shaders/Include/GLSL/DeferredLightingCommon.glslh:31)). That saves position bandwidth and normal storage but introduces encoding/error, sRGB-view, emission-range, and pass-parity contracts. A compact format is only a win if the decode and lighting quality remain acceptable.

At HEAD, commit `b9ec0f117` prototypes splitting a monolithic fullscreen deferred shader into Base (sun/cascades + IBL/GTAO/emission), Punctual (tile point/spot/shadows), and Area (LTC) draws. Punctual/Area blend additively while preserving destination alpha. They execute inside **one render pass** so tile GPUs can retain attachment data; an empty area-light scene skips that draw ([DeferredLightingPass](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/SceneRenderer.cpp:4840)). Debug complexity/cascade views fall back to the monolithic shader. Shared setup is duplicated into a common split include while monolithic remains a comparison reference, imposing maintenance risk.

**Reported result, not reproduced:** the commit records M2 Welcome-scene total GPU frame changes of 41.2 -> 34.7 ms with soft shadows and 23.2 -> 21.2 ms with hard shadows; with four area lights, 53.4 -> 46.6 and 35.1 -> 32.9 ms. Output reportedly agrees to RGBA16F partial-sum rounding. The proposed reason is lower shader live-register/resource pressure, despite more fullscreen draws. `SplitDeferredLighting` is still **false by default**. Those numbers do not predict a desktop NVIDIA/AMD or Lux improvement.

Lux already uses clustered deferred. Its separate feature branch adds an area-light pass when needed; that is not identical to splitting all deferred terms. Lux has render-graph declarations/alias planning and different material/G-buffer contracts; lifting Lucky's pass shaders wholesale would bypass them.

**Decision:** preserve a reference shader and raw HDR comparison if Lux tests register-pressure splits or G-buffer compression. Record shader resource/occupancy data, GPU frame time, pass time, G-buffer bandwidth, and HDR error. Try one controlled split first. Do not infer a win from draw count alone or disable render-graph dependencies to preserve a single rendering scope.

### R9. Shadows: caster geometry and projection conventions matter more than cascade count

Lucky computes logarithmic/uniform blended cascade splits, bounds each receiver slice by a rounded sphere, creates a light orthographic projection, and snaps to shadow texels ([CalculateCascades](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/SceneRenderer.cpp:6414)). It pads small cascades to a minimum 100-unit light-space depth range to catch occluders behind the visible slice. Its [Potential Shadow Caster volume](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/Math/Frustum.h:10) classifies frustum faces against the light, retains the appropriate halfspaces, extrudes silhouette edges along light direction, then sphere-tests the resulting volume. That is geometrically different from camera-frustum filtering: an unseen object can still project a visible shadow.

Current Lux also computes stabilized cascades, with max-shadow-distance-limited splits, active cascade counts, a fallback light direction, an alternate up vector near parallel directions, and texel snapping ([source](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/SceneRenderer.cpp#L3504)). Its [caster mask](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/SceneRenderer.cpp#L6050) checks finite shadow-projection frusta and tiny projected-caster thresholds; static GPU groups and cached shadows reduce repeated work, while moving/settling casters stay live. These are existing systems, not missing features.

**Adaptation question:** does Lux's finite depth padding cover all relevant offscreen casters for a receiver slice, and could a PSC volume tighten/rebalance culling without losing shadows? Test a tall offscreen wall/tree casting into a near cascade, a low sun, and a camera crossing split boundaries. Lucky's minimum 100 units is a heuristic, not a scene-independent solution. Its fixed up axis also deserves degeneracy testing; Lux already handles a near-parallel light/up direction. There is also an internal convention discrepancy to investigate: Lucky's cascade corner literals use -1..1, although its [CMake defaults](M:/LuckyEngine/MAC-Source/cmake/LuckyEngineDefaults.cmake:47) define `GLM_FORCE_DEPTH_ZERO_TO_ONE`, its camera constructs GLM projections, and its [frustum extraction](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/Math/Frustum.h:213) explicitly uses the 0..1 inequalities. Lux's inspected cascade corners use 0..1. This is not evidence that the engines legitimately use different depth conventions: trace the effective projection/build configuration and numerically reconstruct near/far corners before deciding whether Lucky's literals are stale or compensated elsewhere. No shadow failure was reproduced here.

Spot/point shadow maps share an atlas with resolution selected from screen coverage. Lucky sorts candidates by coverage with light-index tie breaks and caps shadowed spots at 16, points at 8. Point lights raster six faces into a reusable cube scratch tier, then convert immediately into a single symmetric-octahedral atlas tile before the next light overwrites scratch ([point sequence](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/SceneRenderer.cpp:3914)). Smaller tiles use smaller scratch tiers. This bounds permanent cube storage but still incurs six raster passes, conversion cost, distortion, filtering/seam rules, and per-frame packing. Per-point caster lists are shared across faces, so the shown loop does not eliminate all face-invisible casters.

Shader-side [shadow mapping](M:/LuckyEngine/MAC-Source/LuckyEditor/Resources/Shaders/Include/GLSL/ShadowMapping.glslh:23) uses cascade-world-texel-scaled normal bias; near cascades can use PCSS while distant cascades use hard comparisons. Point PCSS perturbs directions in a tangent plane, folds into the octahedral atlas, searches blockers using unbiased receiver distance, and applies bias only to final PCF comparisons. The blocker/receiver-distance domain must match; blindly copying NDC-depth formulas is unsafe.

**Failure history:** `3ea3ab8f5` fixed a far split hardcoded to 0.3 instead of 1; `cbf4d1bd4` fixed max-shadow-distance accidentally removing lighting rather than just shadow visibility; `d8369a6d0` added normal bias after acne failures; earlier commits added atlas seams, tiers, and point near-plane fixes. These are good test scenarios precisely because Lucky also got them wrong before.

**Decision:** keep Lux's cached/static-vs-moving shadow design. Compare caster volume construction and shader bias/filtering as focused improvements. Octahedral point storage is a candidate if Lux's actual cube memory/descriptor use is a bottleneck; it is not automatically faster or higher quality. Use captures for atlas occupancy, caster count per face/cascade, update frequency, seam error, and contact-shadow bias.

### R10. Material lighting, AO, and refraction: enforce where quantities belong

Lucky's modern [GLSL BRDF](M:/LuckyEngine/MAC-Source/LuckyEditor/Resources/Shaders/Include/GLSL/BRDF.glslh:1) and HLSL sibling share function signatures/math with a parity script. The modern route includes consistent roughness-to-GGX-alpha clamping, height-correlated Smith visibility, normalized diffuse, and analytic multiscatter compensation. Legacy comparison switches allow side-by-side evaluation. Per-pixel BRDF values are cached rather than resampled per light ([Lighting](M:/LuckyEngine/MAC-Source/LuckyEditor/Resources/Shaders/Include/GLSL/Lighting.glslh:33)). A saturation-preserving clamp scales a bright RGB vector instead of clipping each component independently; it reduces hue shifts but remains an energy-changing approximation.

There are historical traps worth learning from: a LUT sample at `(NdotV,roughness)` must use explicit LOD 0 because these coordinates are not spatial surface UVs; implicit derivatives selected unwanted mips and produced banding. Old direct multiscatter experiments remain in helper files even though the active shared BRDF uses a different Turquin factor. Trace callers before declaring the nearby helper active. Commits `1e2ed8f4e`, `86e773fac`, and the modern BRDF parity tests make this a useful example of implementation history explaining visual artifacts.

GTAO previously multiplied the whole finished scene, darkening direct illumination. Patch `3598a5387` moves GTAO before deferred lighting, binds its term there, removes AO's full-color multiply pass, and applies AO to indirect/IBL lighting only. The current [deferred shader](M:/LuckyEngine/MAC-Source/LuckyEditor/Resources/Shaders/DeferredLighting.glsl:1) and [pass order](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/SceneRenderer.cpp:5744) reflect the repair. Half-resolution AO uses depth-aware 2x2 bilateral upsampling rather than naïve linear filtering; a comparison flag selects the old behavior. More AO parameters are not evidence of better AO if it modulates the wrong term.

Transparency is an area where Lucky's limits are explicit. [TransparentGeometryPass](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/SceneRenderer.cpp:4667) does not implement proper back-to-front depth sorting; it iterates existing draw containers, and rigged transparent meshes are skipped pending an animated forward shader. Transparent materials do not cast colored/translucent shadows in these submission paths. A fallback that silently drops an unresolved material/submesh also deserves comparison with Lux's error-material behavior before copying it.

Its [forward glass shader](M:/LuckyEngine/MAC-Source/LuckyEditor/Resources/Shaders/Include/GLSL/HazelPBR.glslh:441) refracts a direction using IOR, offsets screen UV by thickness with a fixed distortion scale/cap, samples a roughness mip of the opaque preconvolved scene, applies exponential absorption, and mixes with environment reflection using Fresnel. It clamps refraction UV to the screen rather than recovering offscreen transmission. It is a practical screen-space approximation, not geometry thickness tracing or stacked-medium transport. Preconvolution runs when transparency needs it even if SSR is disabled ([guard](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/SceneRenderer.cpp:4724)).

Lux's separate rendering feature branch already has roughness-mip refraction, absorption, and an offscreen environment fallback, while dev has its newer foliage alpha-coverage work. Those branches have diverged and must not be described as one tested integrated renderer. Current Lux's matching cutout sampling between depth/G-buffer/shadow passes should be preserved; Lucky's mere presence of meshlet materials does not supersede it.

**Decision:** compare BRDF evaluation/sampling/normal conventions, color-space views, and AO placement numerically and with furnace/direct-light scenes. Learn the parity-test and A/B techniques. For glass, use Lucky as a clear baseline with known shortcuts and keep Lux improvements where already implemented. Add sorting, skinned transparency, and layer correctness only from Lux's actual requirements and test scenes.

### R11. Bloom, exposure, SSR, and spatial AA: reuse quality methods, count real costs

Pyramid bloom remains Lucky's default. [ConvolutionBloom](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/ConvolutionBloom.h:16) is opt-in and allocated lazily. It first area-downsamples HDR, extracts a bright source into an aspect-correct region of a 512x512 transform grid, computes three independent RGB FFT convolutions against a cached analytic lens-glare kernel, then resolves to the composite. The source's longest side is 256 and the pad radius 120; `256 + 2*120 <= 512` makes source+finite kernel support fit without circular wrap. The kernel is normalized per channel through its DC term and recomputed only when parameters change. Same-image dispatch dependencies get explicit storage barriers ([implementation](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/ConvolutionBloom.cpp:12)). Per-pass descriptor ownership prevents a later mid-frame rebind from rewriting a descriptor earlier commands still use.

**Tradeoff:** fixed low-resolution convolution keeps FFT cost bounded, but limits glare detail, allocates several complex RG32F images, and performs per-channel transforms. Kernel normalization preserves convolution energy; later bloom scaling/addition and threshold/firefly handling still determine the final image's energy. Calling all of it physically exact would overstate the implementation. Lux's feature branch has an FFT spike already, so useful comparison is padding/kernel support, normalization, intermediate formats, stable output cost, descriptor lifetime, and visual impulse response—not “add FFT bloom.”

Exposure uses histogram/adaptation compute before composition, and diagnostic PT views bypass bloom/exposure/tonemapping so normals, motion, material, and validation views retain their intended numeric meaning ([PT composition path](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/SceneRenderer.cpp:5697)). This is a valuable debugging contract independent of artistic exposure preference.

Lucky builds hierarchical depth and a preconvolved scene-color chain for SSR. Those resources and dispatches do not prove the renderer has general hardware occlusion culling. SMAA remains a spatial option and is bypassed while raster DLSS owns reconstruction. Source evidence here establishes sequencing/integration, not that Lucky's SSR edge behavior or AO quality is measured superior to Lux. Detailed per-sample SSR traversal/roughness rejection and a full exposure numerical audit were outside this pass.

**Decision:** prefer a controlled image-quality/cost comparison with Lux's existing effects. Useful tests are single-pixel HDR impulses near screen edges, saturated colored highlights, odd aspect ratios, viewport resize, exposure steps, and diagnostic-view neutrality. Keep temporal reconstruction out of the current implementation priority.

### R12. Path tracing architecture: budgets, sampling, and failure transactions

Lucky's PT is a module that gathers a render snapshot into acceleration structures, geometry/material/light tables, traces rays, reconstructs/denoises, then joins normal composition. It is not just a shader pasted into the raster path.

The [BLAS cache](M:/LuckyEngine/MAC-Source/Modules/Hazel.PathTracing/src/Hazel/Renderer/PathTracing/BLASCache.h:15) keys entries by mesh-source identity, GPU content generation, submesh, and LOD. First sight creates/queues a build but does not return it as ready. The default per-frame budget is four builds and 64 MiB of scratch, with distinct aligned offsets inside shared scratch. A first oversized build can make progress rather than stall forever behind a budget. Recorded build batches require finalization after the submission result; failed work returns to pending. Thus “build commands recorded” and “traversable geometry accepted” are distinct states.

The [scene](M:/LuckyEngine/MAC-Source/Modules/Hazel.PathTracing/src/Hazel/Renderer/PathTracing/PathTracerScene.h:133) rebuilds TLAS in place on one ordered graphics queue, with frame-buffered host-visible tables. It prepares a complete candidate resource set before publishing growth; empty scenes still get a traversable empty TLAS. Static geometry can appear over several frames as budgeted BLAS builds finish, so startup readiness/capture warmup matters. Unused caches use a 120-gather reuse grace period, shortened under descriptor pressure; GPU-safe retirement still follows completion, not 120-frame timing.

Skinned instances use [GPU skinning + per-instance BLAS rebuilds](M:/LuckyEngine/MAC-Source/Modules/Hazel.PathTracing/src/Hazel/Renderer/PathTracing/SkinnedGeometryCache.h:20), with rest/bone buffer generations retained. A previous accepted skinned-pose buffer supplies exact deformation motion. This is more correct than rigid-root-only reprojection, but costs an extra previous vertex stream, copies, skinning, acceleration-structure builds, and memory per semantic instance. It does not demonstrate that skinned BVH refit or update is always used.

[PathTracer.hlsl](M:/LuckyEngine/MAC-Source/LuckyEditor/Resources/Shaders/PathTracing/PathTracer.hlsl:1) uses an inline bounce loop, Lambert/GGX sampling, next-event estimation, MIS for emissive/environment hits, Russian roulette, ray-cone texture LOD, and firefly limiting. [LightBaker](M:/LuckyEngine/MAC-Source/Modules/Hazel.PathTracing/src/Hazel/Renderer/PathTracing/LightBaker.cpp:367) builds a power/spatial light tree on CPU, with directional selection separated from positional lights. Emissive triangle light registration is capped at 4,096 triangles per submesh; larger emitters remain visible through hit emission but lose that explicit sampling route, affecting convergence/noise. This is a bounded-cost compromise to measure, not silently treat as comprehensive emissive importance sampling.

Progressive accumulation and adaptive sampling are separate from denoiser reconstruction. Adaptive state uses Welford luminance variance/count, a relative standard-error threshold, and minimum samples, and is restricted to progressive non-realtime-denoised views. Reaching a sample cap stops tracing and preserves the mean; it is not proof that every pixel converged. Sparse bright paths and firefly clamping affect the estimator. Source limits and optional denoisers are explicit in [settings](M:/LuckyEngine/MAC-Source/Modules/Hazel.PathTracing/src/Hazel/Renderer/PathTracing/PathTracer.h:50).

**Decision:** an excellent future reference for a Lux offline/reference renderer, material validation, thumbnails, or a PT viewport, if those become goals. Start with a small capability-gated view pipeline and exact resource ownership, not the entire denoising/recording stack. Keep CPU retained scene data as a source of stable identity and geometry snapshots. Measure BVH build/skin cost, streaming latency, scratch peaks, descriptor pressure, and output quality. PT presence alone does not justify making it Lux's default or diverting current priorities.

### R13. Temporal lessons for later: distinguish identity, change, and acceptance

The user's current priority is explicit: temporal rendering may return later, but is not a present implementation task. Lucky's failures are still worth studying so Lux does not repeat them.

**Identity problem.** Previous transforms indexed by gather order attach history to the wrong object after sorting, streaming, spawning, or deletion. Lucky uses semantic instance keys (scene entity/component/tile/submesh/imported-node identity plus geometry content generation), sorts flat snapshots, and resolves previous pose per key. A new key gets current==previous. Duplicate keys or mismatched arrays fail without corrupting the old snapshot. Empty snapshots replace old contents. Reused capacities avoid steady-state heap churn ([motion history](M:/LuckyEngine/MAC-Source/Modules/Hazel.PathTracing/src/Hazel/Renderer/PathTracing/PathTracerScene.h:40)).

**Change problem.** Progressive accumulation cannot keep averaging a moving world, but a denoiser is specifically intended to reproject ordinary motion. In commit `e1526d8de`, whole-scene/light hashes had been resetting temporal history every frame while emissive/analytic lights moved, yielding unstable one-sample output. The patch separates full light changes from structural radiance/type/count changes, and separates instance membership churn from content changes on an instance that persists in both frames. It logs reset causes and consecutive-reset streaks. New streamed instances start with zero motion rather than forcing a full-screen reset. That is a policy tradeoff requiring disocclusion handling, not a universal assertion that new geometry can never invalidate lighting.

**Acceptance problem.** A frame rejected by upload/build/dispatch failure must not become next frame's previous pose. `RT_OnFrameResult` commits motion/skinned lineage only after the frame result; pending GPU references survive to actual completion. [FrameSlotUploadTracker](M:/LuckyEngine/MAC-Source/Modules/Hazel.PathTracing/src/Hazel/Renderer/PathTracing/FrameSlotUploadTracker.h:11) tracks which distinct replicated buffer slots contain a generation and marks successful uploads only; repeating the same slot does not establish all-slot coverage. Native buffer recreation resets coverage even if logical content is unchanged.

**Guide problem.** Correct rigid motion is insufficient for deformation and specular reflections. Commit `0ed2a0fc0` adds exact prior skinned vertex/tangent-frame streams, roughness-tapered virtual specular motion, and guide-contract fixes. Earlier `76fb6a419`, `db3cedefd`, `e1cdd9c12`, and later `0a29b5861` record disocclusion, camera motion, ghosting, and cold-start shimmer work. This history demonstrates substantial implementation difficulty, not guaranteed artifact-free temporal output.

**Integration problem.** [UpscalerPass](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/Upscaling/UpscalerPass.cpp:435) keys initialization by device/configuration, canonicalizes supported modes, checks capabilities, retries transient failures with 250 ms -> 8 s backoff, and can initialize asynchronously. Resize/debounce/fallback behavior avoids continuous expensive SDK creation. Requested scene settings remain separate from hardware-effective choices. An enum/type existing in NRI is not evidence the corresponding vendor SDK/preset is available.

The module has [motion-history tests](M:/LuckyEngine/MAC-Source/Modules/Hazel.PathTracing/Tests/src/PathTracerMotionHistoryTest.cpp:127), [content-history tests](M:/LuckyEngine/MAC-Source/Modules/Hazel.PathTracing/Tests/src/PathTracerContentHistoryTest.cpp:71), and a [distinct-slot upload test](M:/LuckyEngine/MAC-Source/Modules/Hazel.PathTracing/Tests/src/FrameSlotUploadTrackerTest.cpp:7). These CPU tests check identity/policy invariants; they cannot prove DLSS output is stable, correct under every driver, or free of ghosting. Boot/mode-switch probes establish survival, not visual convergence.

**Decision for later:** reuse the separation of semantic identity, material/geometry content, ordinary motion, discontinuity, and successful-frame publication. Design the validation scenes before implementation: still camera/moving object, moving camera/still object, skinned motion without root motion, new geometry streaming, deletion/reordered batches, emissive-body motion, resize, failed upload, and long reset streaks. Keep current spatial rendering stable until temporal work is explicitly prioritized.

### R14. Profiling: instrumentation can change the thing being measured

Lucky's [GPUProfileSession](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/GPUProfileSession.h:19) waits for content readiness, warms 120 frames by default, captures 600, records a readiness timeout rather than hanging indefinitely, and reports lost-readiness frames. It disables VSync unless asked otherwise. [GPUProfileCapture](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/GPUProfileCapture.cpp:31) summarizes count/mean/median/p95/p99/min/max/stddev and reports pass occurrence, which matters when a pass only runs occasionally. Query readback is frame-slot-delayed rather than synchronous every timer.

Commit `ea3a7e5c1` adds a subtle correction: on MoltenVK, timestamp markers inside an active/pending render pass split the underlying Metal encoder and inflate frame cost. Default profiling therefore keeps annotations but skips those timer queries; `all` is available and intentionally described as distorting. Native GPU captures run **after** timed sampling. The platform capture implementation is macOS Metal; other platforms have a stub, so its `.gputrace` feature is not a universal RenderDoc replacement. Capture/readiness hooks also account for editor thumbnail work that can otherwise contaminate results.

Commit `b9ec0f117` adds monolithic/split selection and raw RGBA16F lighting dumps, allowing performance measurements and numerical output diffs for the same experiment. That is a better engineering lesson than the standalone speedup number. The public report fields expose whether content ever became ready, how many frames were captured, and the instrumentation depth.

Lux already has Tracy CPU/GPU instrumentation, per-pass/stage timings, golden/performance capture, and threading A/B tools. A proposal to “add GPU profiling” would be obsolete. The concrete question is whether Lux's own timers perturb rendering scopes on its backends, whether profiling waits for asset/cache readiness, and whether identical camera/content/settings are retained between A/B runs.

**Decision:** adapt instrumentation controls and metadata if missing, preserve Lux's existing tooling, and compare A-B-A captures with raw HDR image diffs. Record GPU/driver/backend/build, warmup/readiness, resolution, VSync, pass timer depth, shadow quality, and optional meshlet/upscaler settings. Do not add nested GPU timers indiscriminately and then optimize an artifact of profiling.

### R16. Command arena: bounds, ownership, alignment, and publication are separate problems

Current [Lux RenderCommandQueue::Allocate](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/RenderCommandQueue.cpp#L25) writes a function header, size, and callable into a fixed 10 MiB arena without checking remaining capacity. It rounds payload sizes to function-pointer alignment. The caller then placement-constructs the callable. This is a concrete bounded-storage robustness gap even with one producer.

Lucky's [allocator](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/RenderCommandQueue.cpp:25) computes the complete required size, checks the end pointer, logs exhaustion, returns null, and tracks queue count/byte high-water statistics during execution. [Submit](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/Renderer.h:173) verifies the returned storage before placement construction. Both still use function-pointer alignment rather than a callable-specific alignment contract, so arbitrary over-aligned captures need separate handling.

**The historical failure was not simply capacity.** `ab66b59f40404494b8d2ecf0ada6b1cacf2cc5dc` reports heavy asset import racing main-thread and asset-worker allocations, corrupting function pointers. Its patch added a mutex and bounds checks; its original failure handling silently returned without submitting a command. Current code uses VERIFY instead. Neither dropping an arbitrary resource command nor a build-dependent assertion is a complete explicit recovery policy. Inspect shipping macro behavior and decide whether to grow, spill, fail the frame/startup, or terminate coherently.

Current [Lux Renderer::Submit](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/Renderer.h#L82) already solves producer ownership differently: main fills the arena, render-thread submissions execute inline, and background work enters a thread-safe staging queue replayed on main. Adding Lucky's allocation mutex would not analyze that existing contract. Conversely, a mutex around allocation alone does not include the subsequent callable construction, execution, or queue swap; full publication/consumption must remain ordered.

**Decision:** adapt checked capacity, release-defined failure reporting, callable alignment, and usage telemetry while preserving Lux's existing producer routing unless evidence calls for a different queue. Verify arena exhaustion, large/over-aligned captures, construction exceptions if supported, background import, queue swap and shutdown under both Lux threading policies. The historical Hazel baseline's queue had neither the later bounds checks nor this producer-routing contract; that ancestry explains the shared starting shape but does not decide the best current solution.

### R17. 2D, MSDF text, fonts, and debug overlays: mature algorithms with unfinished limits

**Problem and method.** Small sprites, glyphs, and debug lines should not each require a separate upload/draw. Lucky [Renderer2D](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/Renderer2D.h:22) expands quads to four CPU vertices/six shared indices and lines to two vertices. Defaults are 5,000 quads and 1,000 lines **per buffer chunk**, not hard scene limits. Helpers select chunks by cumulative index count and allocate another CPU/GPU buffer for every frame slot when needed ([chunk selection](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/Renderer2D.cpp:658)). Allocations persist at their high-water mark. At [EndScene](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/Renderer2D.cpp:378), used prefixes upload and produce one draw per populated chunk, grouped as quads, text, ordinary lines, and on-top lines. This reduces draw count but expands/transforms vertices on CPU, duplicates frame storage, and imposes type ordering rather than preserving arbitrary interleaved transparent submission order. Each chunk opens/closes a rendering scope; there is no evidence that this is optimal on tile GPUs.

**Important limits, visible in both engines.** The geometry chunk mechanism does not solve descriptor capacity. Lucky has 32 sprite texture slots (slot zero is white, leaving 31 distinct nonwhite textures) and 32 font-atlas slots. Linear slot searches deduplicate textures, but a new slot writes/increments without a capacity check; the overflow `FlushAndReset` call is commented out in [DrawQuad](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/Renderer2D.cpp:763), and [Flush](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/Renderer2D.cpp:520) is empty. [DrawString](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/Renderer2D.cpp:1416) likewise has no 32-atlas guard. A 32nd distinct nonwhite sprite texture or 33rd atlas in one scene exceeds the table; this is a static bounds finding, not a reproduced crash. Pinned current Lux has the same 32-slot arrays and unguarded writes at [sprite registration](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/Renderer2D.cpp#L793), [font registration](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/Renderer2D.cpp#L1360), and TODO `Flush`. Copying Lucky does not repair it.

Conversely, Lux already fixes one Lucky boundary defect: the transformed textured-quad overload calls `GetWriteableQuadBuffer`, while Lucky writes directly through the current chunk pointer. Lux's [source explains the fix](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/Renderer2D.cpp#L800). Also distinguish working circle routes: Lucky's outlined circles are 32 line segments, and billboard discs use a generated soft-edged texture. Its analytic `FillCircle` appends circle vertices, but EndScene's circle-buffer rendering block is behind [#if TODO](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/Renderer2D.cpp:483); those APIs do not establish an active analytic-circle pass. Normal/on-top lines change pipeline specification fields; verify actual native pipeline selection rather than assuming mutating the description changes a baked NRI pipeline.

**Text reconstruction.** `Font` owns CPU `MSDFData` and an atlas texture Ref; the renderer owns its default proportional/monospace font Refs ([default ownership](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/Renderer.cpp:3355)), while project asset lookup resolves authored font handles with default fallback. [Font.cpp](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/UI/Font.cpp:165) loads glyph outlines/metrics with FreeType, packs a 40-pixel/em MTSDF atlas with a two-pixel distance range, runs the expensive atlas generator with eight workers, and uploads RGBA32F without mips. It includes Latin and Cyrillic ranges, not all Unicode. The [text shader](M:/LuckyEngine/MAC-Source/LuckyEditor/Resources/Shaders/Renderer2D_Text.glsl:70) takes the median RGB distance, scales its range with UV derivatives and atlas dimensions, and reconstructs smooth alpha. It does not consume the fourth MTSDF channel for outlines; allocation precision and bandwidth should therefore be justified against measured edge quality. `DrawString` converts UTF-8 to UTF-32, makes a word-wrap pass using metrics/kerning, then emits glyph quads in a second pass. This is code-point layout with pair advances, not complex-script shaping, bidi, or fallback-font resolution.

**Caching and provenance.** The [atlas cache reader](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/UI/Font.cpp:67) keys only by font name and em size, reads an unversioned raw header/payload without validating file size/dimensions, and caches pixels rather than all glyph metadata; outlines/packing still run on a cache hit. Same-named changed font bytes can reuse stale pixels. These methods, raw cache design, CPU chunking, slot-limit TODOs, MTSDF settings, and median/derivative shader reconstruction already exist in historical Hazel `pr-base`; they must not be credited as new Lucky solutions. Current Lux's inspected [Font.cpp](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/UI/Font.cpp#L71) independently has comparable name/em cache limitations. Lucky's relevant ownership change is moving defaults from process-static `Font` refs into a renderer instance (history `9f3b22a7f`, `b44a096da`); that improves device-lifetime scoping, not glyph rasterization quality. Commit `69935a0e5` changes the 2D target format to float16; its subject does not establish half-precision CPU vertex packing.

**Debug drawing solves a different lifetime problem.** A render frame may occur with zero fixed-rate C# ticks. Consuming the script's debug primitives each render causes flicker. Lucky [DebugRenderer](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/DebugRenderer.h:11) instead builds/publishes a separate command list per callback phase, replays the last published list each render, replaces it when that phase runs again, and clears it when play stops. The ordinary render queue remains consumed per frame. Actual replay sites exist in [Scene.cpp](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Scene/Scene.cpp:682); history `42db3cbf7` introduced the published phase lists. Captured values/Refs provide command lifetime, with per-primitive `std::function` allocation/capture and replay costs; this is not a thread-safe arbitrary-worker queue. The general lesson is to tie debug-data validity to the producer's update phase rather than display-frame frequency.

**Decision and verification.** Keep Lux's fixed chunk-boundary repair; neither engine is a model for safe texture/font overflow yet. A focused Lux change would segment batches with immutable descriptor snapshots or use a bounded bindless route, preserving transparent order and exact GPU resource lifetimes. Validate 31/32 distinct nonwhite textures, 32/33 atlases, 5,000/5,001 quads, alternating overloads at chunk boundaries, mixed text/sprite layers, supported/missing glyphs, corrupt/name-colliding font caches, and stop/start debug persistence. Atlas format reduction is a measured quality/memory experiment, not an automatic upgrade. Compare current Lux debug callback frequencies before adopting phase persistence; the Lucky policy solves its particular fixed-update/render mismatch. This follow-up is source inspection only.

#### The problem

Knowing a component exists does not tell a user how to use it. A generic Help link forces the user to identify the right subsystem, locate the right page and guess whether its examples match the installed engine. The same discovery problem affects an assistant trying to author a working scene.

#### How Lucky connects the editor to human documentation

### 2. LODs: spatial clustering versus attribute-aware topology simplification

#### Same feature label, materially different algorithms

Current [Lux Mesh.cpp](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/Mesh.cpp#L94) builds LODs by quantizing positions into a bounded spatial grid. Vertices in a cell are merged; position, UV, normals, tangents and binormals are averaged. Triangles that collapse to repeated vertices are dropped, and sorted three-index keys remove duplicate triangles. A reduction must save at least roughly eight percent of the source index count. Fixed target ratios are 0.5/0.25/0.125, and generated LODs get distance multipliers 24/48/96. Each generated level appends its own vertices and indices to render geometry; source geometry remains separate for collision and other consumers. Rigged submeshes skip this simplification.

This is simple and self-contained, but grid cells are decided by position rather than topology, material/UV seams or normal discontinuities. Averaging two coincident vertices from different UV islands can change the texture mapping; averaging a hard edge can change shading; spatial merging can change thin geometry. Those are inferred risks of the algorithm, not visual failures reproduced during this investigation. Sorting triangle keys also treats opposite winding as the same geometric triple, another choice worth testing with two-sided meshes.

[Lucky MeshProcessor.cpp](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/MeshProcessor.cpp:92) instead makes geometry conditioning an ordered import-time pipeline:

1. Canonical vertex deduplication; skinned vertices include bone influences in the equivalence streams so distinct skin weights are not merged accidentally.
2. LOD0 triangle reorder for post-transform vertex-cache locality.
3. Optional overdraw reorder with `OverdrawThreshold = 1.05`, allowing a bounded cache-locality tradeoff.
4. Successive simplification from the previous LOD using `meshopt_simplifyWithAttributes`, normal weights of 0.5 per component and border locking. Target ratio is 0.5, per-step geometric error is 0.02 relative to mesh extent, and reduction stops when it stalls at 95% or more of the previous index count.
5. One vertex-fetch remap applied across all levels; LODs share the optimized vertex stream and add index ranges, rather than generating a separate averaged vertex range per level.
6. Build/optimize meshlets and compute bounding/cone data for every eligible LOD.

Defaults and limits are in [MeshProcessor.h](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/MeshProcessor.h:7). Rigged submeshes receive base geometry optimization but not generated LODs or meshlets. This is not a completed skinned-LOD solution.

#### History reveals the failure that shaped the method

`67209c95e730b113bd0329b077cf11ee4818e198` changed position-only `meshopt_simplify` into normal-aware simplification. The diff explains coarse table surfaces darkening because collapses smeared side normals across the surviving top triangles. Border locking was added to prevent independently simplified submesh boundaries cracking. The geometry-cache processor version changed from 1 to 2 in the same commit: changing the algorithm without invalidating old processed data would hide the fix.

This matters more than “Lucky has meshoptimizer.” Their first use of the library still produced unacceptable shading. The improvement came from feeding the right attributes and constraints into it, then invalidating cached output. Normal attributes are included; UVs are not explicitly added as weighted simplification attributes here. Border/vertex topology and original vertices help, but do not prove all UV/textured cases are solved.

#### What to prefer in Lux

**High-value experiment:** keep Lux's retained scene, per-instance GPU LOD selection and indirect grouping, while replacing or comparing only the import-time geometry producer. A normal-aware, border-preserving simplifier is a stronger candidate for authored assets than purely positional averaging. Preserve the existing source/collision geometry contract. Decide whether shared optimized vertices versus independent LOD vertices actually reduces runtime residency after considering all CPU/GPU copies and runtime serialization.

Test hard-edged tables, UV seams, thin railings, disconnected nearby surfaces, cutout foliage and multiple material boundaries. Compare silhouette/normal/texture error at equal screen size, vertex/index bytes, preprocessing/cache time and GPU timings at equal quality. The current Lucky importer disables generated LODs and meshlets when mesh shaders are unavailable: [AssimpMeshImporter.cpp](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/AssimpMeshImporter.cpp:862). Lux already has a conventional indirect LOD path, so copying that capability gate would unnecessarily remove useful LODs from non-mesh-shader devices.

### 3. Meshlet construction: packing input triangles versus optimizing locality

Current [Lux Mesh.cpp](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/Mesh.cpp#L223) walks input triangles in order, grows one meshlet until it would exceed 64 vertices or 124 triangles, and flushes it. A hash map assigns local vertex slots. Bounds are the mean position plus maximum distance; the backface cone is based on accumulated normalized triangle normals and widest deviation, with a disabled-test sentinel for invalid/spread-out cones. Three byte-sized triangle slots are packed into a 32-bit word.

[Lucky MeshProcessor::BuildMeshlets](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/MeshProcessor.cpp:285) uses `meshopt_buildMeshlets` with a cone weighting parameter, then `meshopt_optimizeMeshlet` and `meshopt_computeMeshletBounds`. It stores compact micro-indices with aligned runs, separate descriptor/bounds arrays and quantized cone data. The limits happen to match Lux; the partitioning/bounds/encoding methods do not.

Sequential packing is cheap and can work well when input triangles are already spatially/cache coherent. Meshoptimizer can search a better partition, trading import work for tighter locality, vertex reuse and culling bounds. Its advantage must be measured on Lux's imported mesh order and target GPUs. A smaller radius/cone is valuable only if it translates into rejected work without false negatives. Mirrored/nonuniform scales and two-sided materials need explicit culling tests. Adapt the producer and encoding deliberately; do not assume Lucky's descriptor layout matches Lux shaders because both say “64/124.”

### 4. Geometry cache: avoid repeated processing without publishing partial garbage

#### Mechanism and optimization

[MeshGeometryCache.h](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/MeshGeometryCache.h:13) deliberately caches processed geometry only. Assimp still reads the live node hierarchy, skeleton, materials and animations. This avoids treating an entire imported asset as one stale blob when only geometry conditioning is expensive.

[CacheFilePath](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/MeshGeometryCache.cpp:19) hashes source path, file size, timestamp, processor version and all processing settings into `<project>/Cache/MeshGeometry/<stem>-<hash>.hzm`. The cache can therefore distinguish mesh-shader-capable and fallback processing choices. Cache hits rebuild the triangle cache after loading processed arrays; GPU buffers are created afterward. This saves simplification/meshlet work, not Assimp parse/material loading or GPU upload.

The most valuable correctness method is [TryLoad](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/MeshGeometryCache.cpp:63): validate header/metadata lengths, section offsets/sizes, count prefixes, vertex/index ranges, LOD ranges, meshlet limits/local indices and bone influence counts. Read into **local arrays**, then move them into the imported MeshSource only after all validation succeeds. Corruption becomes a cache miss and ordinary processing starts from intact live import data.

[EditorAssetManagerTest.cpp](M:/LuckyEngine/MAC-Source/UnitTests/src/Asset/EditorAssetManagerTest.cpp:255) corrupts count words, indices, meshlet offsets, meshlet vertex data and truncates the file, asserting both rejection and preservation of the already imported mesh. This tests a real failure contract, not merely save/load symmetry. The tests were read, not run.

#### Limits worth improving before copying

The hash is a metadata key, not a content-addressed dependency graph. A glTF can keep its JSON size/mtime while its external `.bin` changes; importer flags/version are not independently represented. This can cause stale processed geometry in principle. [Store](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/MeshGeometryCache.cpp:272) writes directly to the final path and removes other cache files sharing the same stem. Two assets in different directories with the same filename stem can evict one another's entries. Different capability/settings variants can likewise replace one another. These primarily cause cache churn; concurrent access/crash behavior was not exercised.

Current Lux's geometry generation is in Mesh.cpp, not the guessed `Asset/MeshProcessor.cpp` or `Asset/MeshGeometryCache.cpp` paths (both 404 at the pinned revision). That observation alone does **not** prove there is no cache elsewhere. Recommendation: first profile import time, then add a dependency-aware cache around the verified geometry producer if warranted. Prefer stable source identity, importer/processor versioning, dependency fingerprints, bounded validation, temporary-file publication and cleanup keyed by full source identity rather than stem. Reuse Lucky's validate-then-publish contract and corruption cases.

### 5. Imported node instancing: one geometry can have many placements

#### The bug class

Assimp may expose one `aiMesh` referenced by several scene nodes. Storing one transform on that geometry overwrites earlier placements. It is a representation issue: geometry identity and placement identity are distinct.

This remains visible in **current** [Lux AssimpMeshImporter::TraverseNodes](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Asset/AssimpMeshImporter.cpp#L484): every node reference assigns `Submesh::Transform`. Current [RenderScene.cpp](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/RenderScene.cpp#L466) emits one retained GPUScene instance per submesh using that transform. The fallback submission similarly multiplies by `submesh.Transform`. Source inspection supports a concrete repeated-node placement problem; it was not reproduced by importing a fixture.

#### Lucky's solution and historical evidence

`b9decc839a20d1cd7a967000779d43310eb23c1f` adds a derived placement list per submesh. [MeshSource::BuildSubmeshInstanceTransforms](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/Mesh.cpp:121) recursively accumulates `parentWorld * local`, appending each referenced geometry's transform. Procedural/unreferenced submeshes fall back to their existing baked transform.

[AssimpMeshImporter.cpp](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/AssimpMeshImporter.cpp:264) builds these lists and encloses **all** placements using transformed AABBs. [SceneRenderer.cpp](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Renderer/SceneRenderer.cpp:3442) loops over node placements and feeds each into its ordinary transform/instance batching. Runtime deserialization rebuilds the derived lists too: [MeshRuntimeSerializer.cpp](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/MeshRuntimeSerializer.cpp:344). The original commit's bounds calculation transformed just min/max corners; HEAD uses `AABB::Transformed`, illustrating why a useful historical fix still needs follow-up scrutiny.

#### Fit with Lux

**Recommend a focused correctness adaptation:** retain one geometry/submesh record and represent every imported placement explicitly in Lux's persistent proxies/GPUScene. Include a stable node/placement identity in cached submission and selection data. Invalidate placements and bounds when an asset reload changes its node references. Do not reintroduce Lucky's per-frame full transform rebuilding just to fix the import model.

Test two nodes referencing one mesh, nested rotations, negative/nonuniform scales, runtime pack roundtrip and reimport from N to M placements. Trace collision cooking, picking and editor bounds too: Lucky's renderer fix is verified, but this investigation did not establish that every physics consumer expands the same placements. Lux's acoustic geometry loop also uses `submesh.Transform`, so correct rendering alone would not prove all scene consumers agree.

### 6. Async assets: publication ordering is useful; copying the implementation wholesale is not

#### Lucky's main mechanism

[EditorAssetSystem.cpp](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/AssetSystem/EditorAssetSystem.cpp:58) has one asset worker, a mutex/CV request queue, a completed-response vector and a snapshot of main-thread loaded assets. It wakes every 100 ms to poll loaded-asset timestamps. New or reloaded data is placed into the response vector under a lock. Reload events are enqueued under that same lock, and [RetrieveReadyAssets](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/AssetSystem/EditorAssetSystem.cpp:190) marks events ready only after moving completed responses to the main thread. The intent is to ensure a reload event cannot reach subscribers before the replacement asset is visible.

Shutdown is deliberately ordered: stop/join workers, clear worker-held references, then unload manager assets while the manager still exists. The project-session boundary and manager reference make project ownership explicit. [EditorAssetManager.h](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/AssetManager/EditorAssetManager.h:69) documents main-thread-only manager operations and copied, locked metadata access. Those ownership contracts matter more than whether an API has “Async” in its name.

#### Explicit weaknesses in the source

The source itself records a race in `GetAsset`: two non-main callers can both miss the loaded/ready checks and load independent copies before either publishes. That can duplicate generated dependent assets and handles. Polling scans loaded assets while holding a long-lived snapshot mutex. `EnsureAllLoadedCurrent` first reads snapshot emptiness before locking. The source also flags project asset-directory mutation and the timestamp window after reading a file. These are not proved runtime races in this session, but they prevent treating the implementation as a generally safe concurrent asset service.

`HasPendingLoads` checks a processing flag, request queue and completed vector. There is a small transition between popping a request and setting the processing flag, and monitor-driven loads have their own timing. It is not a substitute for a generation-aware end-to-end readiness contract.

#### Current Lux difference

[Lux EditorAssetSystem.cpp](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Asset/AssetSystem/EditorAssetSystem.cpp#L23) uses a blocking worker queue and an atomic pending count incremented on queueing and decremented only when responses are drained. It does not need a 100-ms wakeup for its queue. [Lux EditorAssetManager](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Asset/AssetManager/EditorAssetManager.cpp#L108) uses asset loading status to avoid repeating ordinary async requests, dependency/dependent maps and data-change revisions consumed by retained rendering.

Neither design is a full proof of cancellation/reload correctness. A useful Lux audit should track request identity, project/asset generation, reload coalescing, stale completions, dependent invalidation and failed terminal responses. Preserve Lux's pending-through-publication accounting; borrow the explicit ordering of replacement publication before notifying listeners. Do not import periodic locking/polling or duplicate-load windows just because Lucky hot reload appears more elaborate.

### 7. Scene ownership and transform semantics

Lucky's [Scene constructor](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Scene/Scene.cpp:161) receives a `Project&`, binds script storage to that project's engine and uses project-owned asset/renderer/dispatcher services. June history (`b7c371438...`, `4622883f7...`, `d56ec8dfd...`, `3fe793e72...`) progressively removed active-project/static-manager assumptions. Opening a project through an event boundary addresses switching halfway through frame/UI work, not just stylistic dislike of singletons.

[ProjectSession.h](M:/LuckyEngine/MAC-Source/LuckyEditor/src/ProjectSession.h:38) groups editor/runtime/simulation scenes, viewports, panel/layout managers, undo/ImGui context and in-flight scene/script/physics/asset-pack work under one project owner. The project member is declared first so it is destroyed last. The intended lifetime contract is that users of project services die before their owner; all async captures and queued render resources still need to satisfy that contract, rather than member ordering alone proving it. Actual [EditorLayer.cpp](M:/LuckyEngine/MAC-Source/LuckyEditor/src/EditorLayer.cpp:2340) still asserts there is only one session, so this is **preparation for multi-project support**, not proof that multiple open projects already work.

Current Lux still has active-project static access in its importer/asset manager. Session-based ownership is worth adapting if project switching, independent previews or background work expose concrete lifetime bugs. A broad singleton-removal rewrite is not automatically the highest-value task; the testable contract is that work for project A cannot publish into project B after switching.

[TransformHierarchy.cpp](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Scene/TransformHierarchy.cpp:86) also makes a deliberate semantic choice. `ComposeChildWorld` composes translation, quaternion and componentwise scale while keeping a shear-free resolved TRS. `DeriveLocal` uses inverse parent rotation and safe division, retaining existing values on near-zero scale axes. A separate `ResolveWorldMatrix` multiplies matrices through the parent chain and preserves shear. These are different worlds under rotated nonuniform parents. This is not a universal “better transform” algorithm: inspect which renderer/physics/gizmo consumers choose which contract before adopting it. The related `docs/no-shear-transform-hierarchy.md` is design context; source and cross-system invariants decide correctness.

### 8. Prefabs: structural reconciliation versus value propagation

The historical Hazel `pr-base` prefab copies an explicit list of components recursively into a private scene and records a prefab/entity link. Lucky's [CopyableComponents.h](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Scene/CopyableComponents.h:14) centralizes independently copyable types while excluding identity/relationship and order-sensitive bodies/controllers. Current [Prefab.cpp](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Scene/Prefab.cpp:172) compares component values by stable component hash, stores per-component overrides and maps prefab source identity to instances. Nested prefabs have separate source/nested-context IDs. [ReconcileChildren](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Scene/Prefab.cpp:1056) matches existing children by nested context first and source identity second, creates missing source children, and removes deleted children while preserving external/nested ownership rules. Current [Lux Scene::PropagatePrefabEdits](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Scene/Scene.cpp#L1365) and `AdoptPrefabBaseEdits` already support override-aware propagation on existing entities. **Recommendation:** when structural prefab edits become a goal, study Lucky's identity matching and ownership flags while retaining Lux variants. ### 9. Undo: direct reversible operations versus scoped value snapshots

[Lucky EditorOperation.h](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Editor/EditorOperation.h:58) defines an `Apply()` operation that becomes its own inverse. `CopyPropertyState` swaps saved/current values through a pointer; `ComponentState` resolves scene/entity UUIDs and swaps/adds/removes a component; entity create/delete stores entity YAML plus script storage; batch operations reverse application order on alternate applications. The [EditorStack](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Editor/EditorOperation.cpp:351) tracks a head, truncates the future on a new edit and applies stored operations for undo/redo. Widget macros coalesce a drag into one operation using a context marker.

This can be much cheaper than serializing a whole scene for a float edit, but it carries pointer and coverage obligations. Raw/copy property states require referenced addresses to remain valid; the header explicitly relies on LIFO restore ordering. `EntitySetParent::Apply` currently obtains `target.Transform()` before its `if (!target)` check, and unchanged parent in one pair returns from the whole batch. These are concrete code-level hazards, not reproduced crashes. There is an explicit TODO to bound stack size, and the header lists incomplete edit categories. The sophistication of a stack does not prove every editor action is undoable.

The parenting history is particularly informative: `05bcb65431d55da2daf4b3c3093f3767f6ab40f0` stores the prior transform matrix with the parent so repeated undo/redo does not accumulate decomposition/recomposition error. The solution is to retain exact state needed for reversal, not to rerun a mathematically approximate inverse repeatedly.

Current Lux uses labelled **per-entity serialized value diffs** with scoped captures, hierarchy-closed patches applied to the live scene and a complete baseline/fallback; settings/material edits can share the stack through closures. [Pinned architecture](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/.claude/docs/Architecture-LuxEngine.md#L556) describes why a roughly 7k-entity scene motivated scoping rather than full-scene serialization on every field edit. Lux already addressed the obvious performance comparison; replacing it with raw-pointer snapshots is not an established improvement.

**Prefer preserving Lux's value/lifetime safety**, measuring scoped capture/patch cost and testing coverage. Borrow exact transform restoration and clearly ordered compound operations where relevant. Lucky's [ExecuteSceneMutation](M:/LuckyEngine/MAC-Source/LuckyEditor/src/EditorLayer.cpp:3586) is a strong boundary for future external tools: verify main thread, focused editor scene and Edit mode before invoking a mutation with an explicit session undo stack. Tools must not obtain history from whichever ImGui context happens to be current.

The [operation tests](M:/LuckyEngine/MAC-Source/UnitTests/src/Editor/EditorOperationTest.cpp:31) cover LIFO, empty boundaries, redo, future truncation and forward/reverse batching. Those tests do not establish pointer lifetime or complete scene-editor coverage.

### 10. Serialization and runtime packs: distinguish fast access from robust delivery

Lucky retains yaml-cpp human-readable scene/project/prefab authoring with large explicit component serialization and `EntityDomain` filtering for client/server. Lux already migrated to rapidyaml with typed compatibility checks; copying the parser choice is not an improvement. Compare preservation of unresolved scripts, references, defaults and failure behavior, not parser names.

[AssetPackFile.h](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Serialization/AssetPackFile.h:13) uses a per-scene map of handle→typed offset/size. [AssetPackSerializer](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Serialization/AssetPackSerializer.cpp:21) reserves index space, writes app binary and payloads, deduplicates shared assets globally by handle, then seeks back to fill the index. A shared texture referenced by many scenes has repeated index entries but one payload. [AssetPack::LoadAsset](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Serialization/AssetPack.cpp:62) tries the active scene index first and falls back to scanning scene maps.

This is seekable lazy asset access, **not proof of world streaming, chunk residency, memory mapping or I/O prioritization**. [CreateFromProject](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Serialization/AssetPack.cpp:222) discovers scenes and prefab references, adds audio assets broadly, and logs missing assets. Failed scene/asset serialization can continue because the fatal exceptions are commented out. `AssetPack::AddAsset` and `Serialize()` are legacy stubs, while CreateFromProject drives the active writer. Read the call path, not isolated method names.

The [index reader](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Serialization/AssetPackSerializer.cpp:118) checks signature/exact version, then trusts scene counts, maps and offsets much more than the geometry-cache reader does. It returns true after loops without the same bounded section-validation contract. The project runtime format has its own exact version. Binary raw structs/`sizeof` fields need ABI/endian/layout review before cross-platform file portability is claimed. “Builds on three operating systems” is not the same as “one binary asset pack is portable across them.”

[RuntimeAssetManager](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/AssetManager/RuntimeAssetManager.cpp:97) deduplicates ordinary queued requests through a pending handle set and returns placeholders. A notable failure-path gap is visible: [RuntimeAssetSystem::TryLoadData](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/AssetSystem/RuntimeAssetSystem.cpp:87) publishes only successful assets; pending handles are cleared when successful assets are synced. Failed loads therefore lack a terminal completion that clears the pending set, so an ordinary failed async request can remain pending rather than retry/report a terminal state. This is source tracing, not a runtime reproduction.

Lux already has hardened export sequencing, bounded manifests and compatibility work. **Keep explicit export failure reporting and self-contained packaging.** Borrow the useful one-payload/many-index dependency organization only if it improves Lux's actual pack format. Apply the cache's validate-then-publish discipline to runtime data. Test truncation, enormous counts, bad offsets, missing/cyclic prefab dependencies, failed decode terminal state and relocation of an exported game.

### 11. Project jobs versus engine/runtime packaging

These are three distinct operations:

Recommended adaptation is a common manifest and explicit prerequisite/dependency validation where Lux's platform packaging is duplicated. ### 14. Node authoring: shared canvas, domain-specific compilation and incomplete caches

#### What is actually present in this snapshot

The current tree contains **animation, sound and robot motion graphs** backed by a shared native graph editor. The full tracked-path/source searches for `PodComponent`, `PodGraph`, `ProceduralMesh` and corresponding procedural geometry implementation returned no matches. Later public 2026.3 documentation describes procedural graphs; that must not be projected backward into this 2026.2 checkout. No procedural geometry dependency/rebuild system can be audited from absent source here.

Historical Hazel `pr-base` already includes `NodeGraphEditor`, `NodeEditorModel`, AnimationGraph and SoundGraph files. Lucky reuses that framework for MotionGraph; history `55374b8f0` introduces RobotControllerComponent/MotionGraph in November 2025. It is an inherited authoring method extended to a new domain, not evidence that Lucky invented all three graph systems.

#### Shared authoring does not mean a shared runtime

The problem is avoiding three implementations of canvas interactions, typed pins, graph properties, selection and layout while keeping sound, skeletal pose and robot state semantics independent.

[NodeGraphEditorBase](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Editor/NodeGraphEditor/NodeGraphEditor.h:90) is an asset editor over `ax::NodeEditor`. Its [initialization callbacks](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Editor/NodeGraphEditor/NodeGraphEditor.cpp:248) delegate graph/node layout save/load to the model rather than using a global node-editor settings file. Layout positions and view state are JSON strings alongside the asset; they are not the executable graph. [NodeEditorModel.h](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Editor/NodeGraphEditor/NodeEditorModel.h:12) defines node/link access, factories, pin compatibility, serialization and compile/play callbacks. `IONodeEditorModel` adds named inputs/outputs/local variables through `PropertySet` and `choc::value`.

The shared [link validation](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Editor/NodeGraphEditor/NodeEditorModel.cpp:304) checks presence, direction, storage/type compatibility and same-node links. Its `CausesLoop` enum is **not** proof of a general DAG cycle detector: the IO override around line 972 adds a particular same-local-variable check. Domain sorting/validation still needs scrutiny for arbitrary cycles.

Domain models turn editable nodes into runtime **prototypes**: node type/IDs, default-value endpoints, connections and subgraph structures. Factories instantiate actual runtime processors and bind typed endpoints. For example, [MotionGraphFactory.cpp](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Robots/MotionGraphFactory.cpp:636) initializes model-sized buffers/processors and dispatches different value/event/local-variable connection types. [MotionGraphNodeEditorModel.cpp](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Editor/NodeGraphEditor/MotionGraph/MotionGraphNodeEditorModel.cpp:721) validates model assignment, output nodes, factory types, missing links and blend-space geometry before constructing the replacement prototype. “Compile” here is graph validation/order/prototype construction, not automatically a shader compiler or a procedural mesh evaluator.

[MotionGraphEditor::SetAsset](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Editor/NodeGraphEditor/MotionGraph/MotionGraphEditor.cpp:162) reloads a private asset copy for editing, so compiling a candidate does not immediately replace the manager's shared asset. The comment frames discard-without-saving as a future possibility; the copy alone does not prove a complete transactional Save/Revert workflow.

#### Invalidation, last good output and cache boundaries

The IO model has a dirty-player state. [Node/link changes](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Editor/NodeGraphEditor/NodeEditorModel.cpp:996) invalidate it; property rename/type changes adjust associated pins/links and invalidate compiled structure. [Property-value handling](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Editor/NodeGraphEditor/NodeEditorModel.cpp:843) distinguishes potentially live parameter changes from changes requiring rebuilt data readers, such as wave assets and local variables. Source TODOs explicitly call out incomplete invalidation for other asset types. This is a small mutation-classification scheme, not incremental recompilation of only dirty subgraphs.

[SoundGraphNodeEditorModel](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Editor/NodeGraphEditor/SoundGraph/SoundGraphNodeEditorModel.cpp:82) sorts the graph, builds a prototype, creates/validates a player, suspends audio processing, rebuilds streaming sources and replaces the preview player. [OnCompileGraph](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Editor/NodeGraphEditor/SoundGraph/SoundGraphNodeEditorModel.cpp:260) clears dirty and saves the new prototype only after compile success; a failed compile retains the prior usable prototype. Motion compilation likewise assigns `motionGraphAsset->Prototype` only after successful construction around line 919. This is the useful publication contract: invalid edits can remain editable without destroying the last good runtime representation.

Sound graphs have a [prototype disk cache](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Audio/SoundGraph/Utils/SoundGraphCache.cpp:36), with storage under the project cache and count-based removal of oldest files. It uses graph filename stems as keys in the inspected model. [Deserialize](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Editor/NodeGraphEditor/SoundGraph/SoundGraphNodeEditorModel.cpp:512) explicitly leaves checking whether the authored graph is newer than the prototype as a TODO. Same-stem collisions, node-definition/schema versioning and dependencies therefore deserve tests; this is not the dependency-aware geometry-cache design from section 4. Motion and animation prototype caching is still commented out/TODO in the inspected construction code. Do not infer caching everywhere from the shared canvas.

The sound preview uses busy waits for `IsSuspended()` without a visible timeout in these paths. That may block the editor if the audio processing handshake cannot complete; the mechanism is verified, while such a hang was not reproduced here. Specify stable IDs, schema migrations, cycles, edit/undo coverage and live-parameter versus structural edits first. ## Runtime, simulation, ownership, and automation

### 1. The most useful runtime lesson is explicit lifetime boundaries

**Problem.** A process can have multiple applications/projects/tests, while some third-party libraries only support one process-wide instance. Treating every system as a singleton hides dependencies and makes startup, project switches, headless tests, and shutdown fragile. Treating every system as independently instantiable is also wrong for CoreCLR/Jolt/JPL.

**Lucky's method.** The June lifecycle work separates three ownership levels:

1. `Application` owns its renderer/window/services and keeps the scripting host alive while projects change.
2. A `Project` owns its `ScriptEngine` and physics API/resources. `ScriptEngineContext` explicitly supplies nonowned input, time, dispatch, audio, window, and auth pointers; headless services can be null.
3. `ScriptHost::Acquire()` and `JoltCore::Acquire()` share the unavoidable process-level CoreCLR and Jolt registration state. A mutex protects acquisition and a weak reference avoids making the service immortal. Each project ScriptEngine has its own uniquely named assembly load context.

Sources: [Application service construction](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/Application.cpp:177), [ScriptEngineContext](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Script/ScriptEngineContext.h:17), [ScriptEngine constructor/destructor](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Script/ScriptEngine.cpp:25), [ScriptHost acquisition](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Script/ScriptHost.cpp:226), [JoltCore acquisition](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Physics/JoltPhysics/JoltCore.cpp:66).

**History that explains the method.** `8f5f8fed6` introduced the shared ScriptHost because CoreCLR cannot be spawned twice in a process. `c7e2865f76c76286f6b04095c0a9b2b9cc58088b` moved ScriptEngine to each project and reworked destruction ownership. `9cbf8cdf86cd61e12da766ca8b9fc1e56a0a1c38` extracted Jolt registration into JoltCore so multiple JoltAPI instances could coexist. `ced9b4610` then made actual Project/Scene construction usable in windowless engine tests. These are related problem/solution steps, not independent feature additions.

**Limits.** The refactor does not establish arbitrary multi-world execution: `JoltScene` still has `s_CurrentInstance` and explicitly rejects a second physics scene; `GrpcStepSystem` has a single active runtime scene pointer; several script glue component maps remain process-level. A dependency pointer bag requires its owner to outlive every borrower. Do not infer isolation from the existence of per-project objects.

**Compared with Lux.** Current [Lux ScriptEngine](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Scripting/ScriptEngine.cpp#L67) is one process singleton holding the host, load context, current scene, metadata, and managed handles. Current [Lux PhysicsSystem](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Physics/PhysicsSystem.cpp#L56) similarly keeps global registration/resources. This is a simpler design for one active project, not evidence it is automatically wrong. Lucky's separation becomes valuable for concurrent previews, isolated headless tests, multiple project lifetimes, or independent subsystem startup. A focused Lux adaptation would separate process host lifetime from project script lifetime first, rather than blindly replacing all singletons.

**Verification needed before choosing.** Repeated project open/close, multiple engine fixtures within one process, script reload during scene replacement, partial initialization failures, and shutdown with worker callbacks still pending. Track live native/managed resources across the cycles. Agent-authored design explanations are hypotheses to verify, not user intent.

### 2. Weak references: learn the failure and audit the proposed fix

**Lux now.** Its [WeakRef](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Core/Ref.h#L241) stores a raw object pointer, checks a live-address registry, and exposes direct dereference and `dynamic_cast` through that pointer. `IsValid()` only answers whether that address is currently registered; it neither pins the object nor identifies an allocation generation. Deleting and reusing an address can make an old weak reference appear valid for a different object. Checking validity and then dereferencing also has a destruction window when threads are involved. Lux already uses the atomic decrement's returned value to decide final deletion, so that part should not be presented as a new missing fix.

**Lucky's change.** `19203440e8f972356a77c4c2add5d0f1deb64046` describes actual weak-reference use-after-free and final-reference races. The patch:

- Uses the returned atomic decrement to choose one deleting thread.
- Allocates a separate `WeakBlock` only when an object first acquires a weak reference. The block has its own weak count and an atomic instance pointer, and survives after the object dies.
- Clears the instance in the base destructor, and adds compare-exchange increment only when the intrusive strong count is nonzero.
- Removes direct weak dereference; callers must `Lock()` to a strong Ref before use. A queued physics synchronization now checks both the locked body and its entity.

Sources: [RefCounted/control block](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/Ref.h:13), [Lock](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/Ref.h:353), [body synchronization](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Physics/JoltPhysics/JoltScene.cpp:676). The historical Hazel baseline used the older live-address pattern.

**Cost/benefit.** The API encourages safe ownership and the separate block solves stale address identity after completed destruction. Ordinary strong-only objects avoid a separate block allocation. Weak users pay an allocation and atomic weak bookkeeping.

**Important unresolved source-level concern.** Lucky's `Lock()` loads the object pointer from the block and then calls `instance->TryIncRefCount()` on a counter **inside the object**. Another thread can release the last strong reference, run destruction, and free the object between those two operations. The separate block staying alive does not itself pin the allocation containing the strong count. The source therefore does not prove `std::weak_ptr`-equivalent concurrent safety, despite the commit's claim. This is a concrete interleaving concern, not a crash reproduced in this study; external synchronization may make particular call sites safe. A replacement should keep the strong count in independently live storage or otherwise synchronize locking against final release, and prove the invariant.

**Choice for Lux.** Investigate Lux's weak call sites and their thread/lifetime contracts. Adopt the ownership requirement (lock before use, reliable allocation identity), but do not copy this implementation as a proven concurrency fix. Tests must overlap the last strong release with repeated weak locks and force address reuse; a sequential churn test alone does not cover the interleaving.

### 3. TimeManager: multi-rate scheduling, not a generic task scheduler

**Problem.** Physics, control, sensors, dataset rows, and video can run at different frequencies. Driving each from its own float accumulator or from editor refresh can change action/observation ordering, drift timestamps, and make replay depend on rendering speed.

**Actual implementation.** [TimeManager.h](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/TimeManager.h:18) supports at most eight runner slots. It schedules Acquisition → Control → Physics → Validation → Export, plus optional free updates before and after those phases. For each deterministic event:

1. Find the smallest integer-nanosecond time until any runner is due.
2. Push precisely that interval into every active runner.
3. Capture current step durations before the push rotates a runner's fractional-period sequence.
4. Build an eight-bit due-runner mask.
5. Run the precomputed callback list for that mask in each phase, giving each callback its runner's dt and the other runners' alpha/step values.
6. Advance simulation time after the phases, so all consumers within the event see the same timestamp.

Sources: [baking callback permutations](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/TimeManager.cpp:56), [deterministic event](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/TimeManager.cpp:586), [fractional period generation](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/TimeStepRunner.hpp:145), [sync point timestamp latch](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/SyncPointSystem.cpp:12).

**Optimization.** Rebuild each phase's sorted callback arrays at registration/config changes, not every tick. There are up to 256 runner masks per phase; callbacks are flattened and stable-sorted by priority. A `FastCallback` is an instance pointer plus a function pointer, avoiding a captured `std::function` for fixed work. `PausePhaseCaching/ResumePhaseCaching` amortizes startup registration. This trades setup time and duplicated callback storage, exponential in runner count, for a small hot loop. Raising the runner limit is not free.

**Clock precision.** `set_hz` generates a repeating sequence of integer-ns durations from rounded cumulative ideal time, bounded to 32 entries; this handles common fractional-ns periods more faithfully than rounding every 30/60 Hz step the same way. It should not be described as exact rational scheduling for every possible frequency. `0af4c819e07c56a6053a32defb2d0a69394b3fac` removed a 100 ns near-coincidence merge tolerance; the actual patch matters because coalescing nearby events can alter which phases run together.

**Three modes.** Realtime non-deterministic mode can drop excess steps. Low-performance deterministic mode processes all simulation events but allows simulation to fall behind wall time; CPU/UI budgets limit how much is done per display frame. High-performance deterministic mode removes wall-time pacing and runs as many complete events as its budget permits. EMA overhead estimates influence batching/UI pacing, not the logical next-event sequence. A slow callback cannot be preempted; the budget is checked between events. Deterministic scheduling does not prove cross-platform floating-point, physics, random generator, or neural rendering determinism.

**History.** `8f4112f1ef96197b4f1836afd7814aecf8a1ddd7` introduced the initial scheduler (its subject reports an 11× speedup, not independently reproduced here). `49e3b4977` moved scene updates through it, and `f3a9de2d74309a3cb9837cb471661d0ce153489a` removed physics accumulators so there is one timing authority. `61ef4b589` added strict UI responsiveness. Reading this sequence explains why the system exists.

**Lux comparison and choice.** Current [Scene::OnUpdateRuntime](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Scene/Scene.cpp#L792) invokes script OnUpdate with frame dt, then calls StepPhysics; [PhysicsScene::Simulate](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Physics/PhysicsScene.cpp#L825) owns its accumulator/substep policy and also offers SimulateStep. For gameplay this is simpler. The valuable principle is one explicit fixed-step authority and documented ordering between scripts/controllers/physics, not necessarily all five robotics phases or all-mask caching. First test a force applied in a script at 30/60/144 display Hz, pause/single-step, root motion, and collisions before deciding if Lux needs a fixed-script hook or a larger scheduler. Keep display-rate UI/audio needs explicit.

### 4. Threads and workers: different architectures must not be conflated

LuckyEditor's [binary configuration](M:/LuckyEngine/MAC-Source/LuckyEditor/src/LuckyEditor.cpp:509) selects `ThreadingPolicy::SingleThreaded`. Render submissions are deferred on that same main thread; dedicated rendering exists in multithreaded runtime configurations. The TimeManager runner callbacks execute serially when the scene drives them; phase names do not imply worker threads. Current Lux Windows defaults to a real render thread; Linux's default differs. A Lucky main-thread shortcut cannot be transplanted into Lux without tracing that difference.

Lucky's one-shot jobs generally have a `Start` factory, a `std::jthread` declared last so it joins before borrowed members die, atomics publishing completion, locked progress, and a one-time main-thread result handoff. [ImportProjectJob](M:/LuckyEngine/MAC-Source/LuckyEditor/src/Utilities/Content/ImportProjectJob.h:22) and [its worker launch](M:/LuckyEngine/MAC-Source/LuckyEditor/src/Utilities/Content/ImportProjectJob.cpp:126) are useful concrete patterns. The guidance describes stop-token cancellation; this particular import job's actual `RunBackground()` has no stop-token parameter, so cancellation cannot be assumed just because it uses jthread.

Current [Lux JobSystem](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Core/JobSystem.h#L11) is a separate fork-join pool: workers plus caller share disjoint parallel ranges; zero-worker policy runs inline. It is already used for retained-scene transform work, and is separate from Jolt's pool and the render thread. A one-shot I/O job, a fixed-phase scheduler, and a fork-join CPU pool solve different problems. Preserve those distinctions.

**Choice.** Use explicit job lifetime/result handoff for long editor operations; use Lux's pool for bounded CPU fan-out; keep GPU submission under Lux's existing renderer contract. Validate shutdown while jobs are active and cancel only at points the implementation actually supports. A source convention such as “no GPU on workers” must be checked against real exceptions: FFmpegWriter has a recording render worker and synchronized NRI work.

### 5. Modules: optional capability negotiation and orderly teardown

**Problem.** A renderer feature such as path tracing needs optional device extensions before device creation, capability checks after device creation, feature shaders at renderer startup, and teardown before the renderer/device die. A Boolean setting inside a giant renderer cannot express all of those stages reliably.

**Method.** [Module](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/Module/Module.h:15) exposes a descriptor, named dependencies, side-effect-free requirement checks, load/background-startup hooks, renderer hooks, and polled shutdown. Checks return Pending, Unsupported, Degraded, or Supported; optional failures become visible dormant modules and required failures become startup errors. [Application](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/Application.cpp:177) evaluates in waves, lets hooks request extensions before device creation, publishes actual graphics capabilities, makes the final requirements decision, then supplies shader manifests and loads supported modules with explicit services.

**Ordering/optimization.** [Registry sorting](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/Module/ModuleRegistry.cpp:59) uses deterministic topological order with lexical tie-breaks rather than registration order. The implementation scans vectors to find dependencies and ready nodes: acceptable startup work for a small module set, not a high-throughput graph engine. Missing named dependencies warn and are ignored for ordering, so DependsOn is not a hard proof another subsystem exists. Cycles become fatal/dormant failures. Each loaded module gets a tagged HeapArena for attributable long-lived allocations; this is telemetry and ownership policy, not evidence every ordinary allocation is routed through it.

**Shutdown.** [UnloadModules](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/Module/ModuleRegistry.cpp:309) polls in reverse load order and only retires a module when it is done and **all later-loaded modules** are down. This conservatively orders more than direct graph dependents. It yields for 64 polls, then sleeps 1 ms and periodically warns. There is no hard timeout. Module-owned worker drains may progress; the render queue is not pumped here, so waiting for a newly queued render command can deadlock, especially in single-threaded mode. The contract explicitly requires earlier GPU flushes.

**History and limits.** `de52bfbfee59a2402d2c700b6b7735c61a2b11e9` is titled “First pass at module refactor”; it extracts the actual path-tracing implementation into `Modules/Hazel.PathTracing`. Generic comments list scripting/audio as possible modules, but that is not proof they are already modularized. The separate Hazel.Memory submodule's internals were unavailable in this checkout; only its module integration calls were inspected.

**Lux choice.** Adapt if Lux needs independently optional rendering/simulation/tool packages and capability fallback. The first unit should have a real lifecycle problem to solve. Keep Lux's NRI lifetime/synchronization approach under review rather than treating any existing agent-authored design as mandated. Do not build a plugin framework merely to imitate a directory layout. Test unsupported hardware, disabled optional module, required capability failure, repeated load/unload, and worker/GPU-drain teardown.

**Lucky flow.** Scene registers Jolt callbacks in the TimeManager phases. [Acquisition](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Physics/JoltPhysics/JoltScene.cpp:107) bulk-adds queued bodies; Control calls PreSimulate; Physics updates characters then calls `JPH::PhysicsSystem::Update(ts, 1, allocator, pool)`; Export calls PostSimulate and capture/contact work. [PhysicsScene pre/post](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Physics/PhysicsScene.cpp:99) separates scene-to-physics transform changes from physics-to-scene updates.

**Concrete constraints.** [JoltAPI](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Physics/JoltPhysics/JoltAPI.cpp:11) reserves `300 * 1024 * 1024` bytes of scratch, despite a stale `//10 mb` comment, and constructs a pool with six worker threads. [JoltScene](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Physics/JoltPhysics/JoltScene.cpp:36) allows only one current instance and hardcodes body/pair/contact capacities. These are product/workload decisions to measure, not sensible universal defaults.

**Lux flow.** Current Lux already has Jolt bodies, colliders/cooking, queries, controllers, contact events, and fixed stepping. **Historical Hazel.** `pr-base:Hazel/src/Hazel/Physics/PhysicsScene.cpp` had a local float accumulator and SubStepStrategy. Lucky's January 2026 change removed it in favor of the shared scheduler. Lux's resemblance to the older accumulator is a method comparison, not a lineage claim.

**Choice.** Investigate bulk body creation for Lux loading/spawning and verify controller/physics ordering. Keep hardware-aware pool sizing and select scratch/capacities from observed peak requirements. For a scheduler change, choose who owns fixed timing before moving callbacks; two accumulators in series can create missed/double steps. Verify moving-platform contact, jump, kinematic motion, parented bodies, add/remove during play, and sleeping-body edits.

### 7. Coral scripting: ownership, reload, ABI, and authored data

Both engines already use Coral. Even the inspected Hazel 2024 baseline includes Coral; “adopt Coral from Lucky” is not the useful question.

**Lucky's method.** Each project owns a ScriptEngine/ALC, while the application retains the shared process ScriptHost across switches. A scene ScriptStorage gets a nonowning back-pointer; [SetCurrentScene/destructor](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Script/ScriptEngine.cpp:60) clears that pointer before engine teardown. Assembly failures reset failed AssemblyData so later type iteration does not dereference a nominally present but failed assembly. Destruction releases field defaults, unloads the ALC, runs collect/finalizers/collect, and deliberately **does not clear the process-wide Coral TypeCache** while other engines may still use its Type pointers.

[ScriptEngineScope](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Script/ScriptEngine.h:365) is a nestable RAII thread-local current-engine pointer for native glue callbacks that cannot receive a C++ context explicitly. Scope destruction restores the previous pointer. It removes a global active-project lookup but requires every managed-entry thread to have a scope; gRPC pool threads lack it, leading to specialized marshalling/registry paths. Some glue maps are still globals, so this is not full context isolation.

**Lux comparison.** Current [ReloadAppAssembly](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Scripting/ScriptEngine.cpp#L276) clears live handles and metadata, unloads its sole ALC, clears TypeCache, collects, recreates the ALC/core, and registers glue. That is coherent with one engine/ALC; copying Lucky's per-project ownership without revisiting TypeCache clearing would create dangling metadata in other engines. Lux already has shadow-copy assemblies, scene field storage and unresolved-script preservation. Those must survive any host refactor.

**Interop evidence.** [ScriptGlueHelpers](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Script/ScriptGlueHelpers.h:94) uses plain uint64 handles because wrapper UUID/AssetHandle classes do not have a reliable shared ABI. `e6ede1dff` fixes Linux Coral Boolean behavior; `6d389b850` fixes deterministic field ordering. These are valuable prompts to trace field size, signedness, array ownership, struct layout, calling convention, and declaration ordering, not just compare method names. Generated bindings and runtime reflection still need ABI tests.

**Choice.** Prioritize repeatable play/stop/reload and native-to-managed lifetime invariants; split host/project ownership only when its isolation benefit is required. Validate inherited fields, arrays, entity references, unresolved scripts, assembly failure, reload after build, and Release/Dist on supported platforms. Do not reintroduce an old missing-lifecycle claim from the May Lux snapshot.

### 8. Animation: compressed tracks, root-motion timing, and graph lifetime

**Problem.** Skeletal animation must balance memory, sampling cost, blending, root-motion continuity, asset reload, and physics timing. The asset/graph editor being present does not solve those questions.

**Pipeline.** [AssimpAnimationImporter](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/AssimpAnimationImporter.cpp:252) maps channels to skeleton indices, reserves channel zero for artificial root motion, derives missing/default tracks, and can extract selected root translation/rotation components. It transforms root motion into a common reference frame with an identity first root pose, permitting blends across clips. [Compression](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/AssimpAnimationImporter.cpp:596) builds ACL QVV tracks, preprocesses, and compresses at import time. Runtime [AnimationNodes](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Animation/Nodes/AnimationNodes.cpp:65) maintains an ACL decompression context, seeks to time, and writes directly into reusable pose storage.

**Optimization and precondition.** [PoseTrackWriter](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Animation/PoseTrackWriter.h:14) skips default translation/rotation/scale subtracks because the destination pose has already been filled with the skeleton rest pose; it skips root scale and uses SIMD store helpers. That optimization is correct only if initialization/reset actually satisfies the precondition. Root-motion code separately handles forward/backward loop wrap, and time changes resample to establish the next delta baseline. Retargeting caches a bone map when clip and target skeleton differ.

**Graph mechanics/costs.** [Graph::Process](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Animation/AnimationGraph.cpp:221) traverses its node list; endpoint streams refer to graph storage, and state-machine transitions may evaluate source and destination with synchronized time scaling. This is not evidence of a SIMD job scheduler or crowd-animation batching. [AnimationGraph](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Animation/AnimationGraph.cpp:279) explicitly stores a raw Skeleton pointer to avoid repeated asset lookup/refcount traffic and notes the need to rebuild graph instances on skeleton reload. [NodeProcessor](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Animation/NodeProcessor.h:123) warns that introducing a new input into an existing graph without supplying a default can cause validation failure or a null dereference. These are concrete cache invalidation/schema-evolution costs.

**History.** ACL decompression/root motion already appear in historical Hazel `pr-base`; do not attribute all animation engineering to Lucky's later fork. `b223337ed0329675ae82b140abd0867a175fa96a` fixes “root motion not moving character” by changing animation's scheduled location so its outputs exist before physics consumes them. It edits scene settings/serialization, not the sampler: a strong example of a correct algorithm failing because its integration order was wrong.

**Lux choice and evidence limit.** A complete recursive tree of current Lux contains animation/skeleton editor icons but no dedicated animation implementation directory. Its [Mesh.h](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/Mesh.h#L270) retains bone structures/buffer access and a dynamic-mesh comment, while skeleton/animation accessors and stored skeleton/clip members are commented out. [Components.h](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Scene/Components.h#L560) retains BoneEntityIds; the current importer includes Assimp's bone-weight limit flag but no clip/skeleton processing was found in that file. These inspected paths do not establish an equivalent complete active skeletal/graph pipeline; icons and scaffolding do not prove it exists. This is a stronger bounded source finding than an absent guessed filename, but not a runtime audit of every downstream consumer. If animation work is scheduled, trace the remaining import/component/render consumers and prioritize a small complete path—import, compressed sampling, blending, root motion, skinning, reload—before inheriting Lucky's graph/editor/robot-controller coupling. ### 9. MuJoCo and robotics: valuable control/observation contracts, specialized product scope

**Why two physics integrations.** Lucky has ordinary Jolt gameplay physics and MuJoCo model/data instances for articulated robot simulation, sensors, actuators, policies, and training. Source does not establish one joint solver that automatically couples Jolt and MuJoCo bodies. Avoid presenting this as a free physics quality upgrade for Lux.

**Method.** [MujocoSceneInstance](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Physics/Mujoco/MujocoSceneInstance.h:82) owns compiled model/data, ECS mappings, buffers, visual/physics assets, and per-instance policy application. The split [Acquisition/Control/Physics](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Physics/Mujoco/MujocoSceneInstance.cpp:2982) path sets external wrenches, sanitizes state, neutralizes policy-owned actuators **before mj_step1**, computes controls/policies, applies gravity compensation as the designated force writer, calls mj_step2, and clears transient wrenches. Another mode runs exact substeps without a local accumulator; policy runtimes are ensured loaded before the first actuator-neutralization decision so episode zero matches subsequent episodes.

**Ownership is part of correctness.** [PolicyApplier](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Robots/Policy/PolicyApplier.h:22) owns runtimes per (entity, policy-slot), sorts/application-orders by priority, tracks claimed joints, and owns a session cache that outlives borrowed runtimes. It reseeds controller targets after teleport and resets policy-controlled joints outside an agent's own joint list. Otherwise the next PD control step can yank a teleported robot back or leak the previous episode's state. `Reset` explicitly clears warm-start/scratch state before full forward dynamics; kinematic refresh and simulation-ready reset are different operations.

**Optimization.** [PolicyNetwork](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Learn/PolicyNetwork.cpp:66) caches names/session configuration, uses one intra-op thread with deterministic inference requested, and runs batches into preallocated observation/action buffers. The per-instance PolicyApplier path is more scoped than the older process-global network cache, so these are related mechanisms, not one unified ownership model. No throughput claim is made here.

**Import/runtime boundary.** [MujocoVFS](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Physics/Mujoco/MujocoVFS.cpp:27) builds a MuJoCo VFS from packed file entries with bounds/error handling, normalizes its lookup names to MuJoCo's basename/lowercase semantics, and invalidates the entire VFS on a failed entry. Root scale is explicitly warned as not propagated into the MuJoCo model. Coordinate conversion, compile-time versus runtime state, multiple geometry/material sources, and asset name collisions all matter before reusing this integration.

**Choice.** For Lux, retain the transferable lessons: one writer per control quantity, explicit force/pose ownership, controller reseed on teleport, deterministic reset of hidden solver state, and preallocated batch I/O. Import MuJoCo/ONNX/training product layers only if robotics or articulated-control simulation becomes an explicit Lux goal. LuckyLab is retired and absent; LuckyRobots is a separately distributed SDK, not a vendored source tree in this checkout.

### 10. gRPC: phase-correct snapshots and a deliberately blocking action gate

**Problem.** RPC handlers run on a worker pool, while Scene/ECS/rendering are main-thread owned. Waiting for a main-thread dispatcher at the wrong moment deadlocks if the main thread is itself waiting for an external action. Capturing camera data at arbitrary editor refresh time can return a pre-action image alongside a post-action state.

**Actual Step path.** [AgentService.Step](M:/LuckyEngine/MAC-Source/Hazel-ScriptCore/Source/Hazel/Net/Grpc/Services/AgentServiceImpl.cs:140) requires a registered external AgentBatch. The handler queues camera requests, writes thread-safe external action snapshots, signals the external-action gate **before** any wait for main-thread service, then awaits an observation frame counter on the worker. It handles a reset-frame baseline to avoid consuming/skipping the wrong first observation. Tick-only Step is a gated advance for a registered agent, not an agent-free general scene step.

[ExternalActionGate](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Learn/ExternalActionGate.cpp:56) uses atomic wait/notify in Acquisition. It intentionally blocks the simulation/main thread until an action arrives. A watchdog wakes it on disconnect/timeout. Reset/stop deactivate the gate from the worker first so the main thread can drain the reset request. The watchdog invokes its timeout effect before waking the waiting thread and avoids calling its own join path. This is specialized synchronous external simulation control, not ordinary nonblocking editor work.

[GrpcStepSystem](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Grpc/GrpcStepSystem.cpp:67) consumes requests during Export, resolves cameras on the owning thread, captures color/metric depth, copies pixels into owned vectors, and signals a condition variable. [GrpcMainThreadDispatcher](M:/LuckyEngine/MAC-Source/Hazel-ScriptCore/Source/Hazel/Net/Grpc/GrpcMainThreadDispatcher.cs:105) drains up to 256 queued work items per pump; TaskCompletionSource continuations run asynchronously rather than reentering engine code inline during completion.

**Costs/limits.** Camera captures can involve render/readback stalls and a full pixel copy per result. The C++ capture state has a single pending request batch and a single ready batch, not per-request correlation; concurrent Step callers need serialization outside this object. The static active system is a nonowning atomic raw pointer. Clearing it at stop and waking waiters is useful but does not itself prove safe lifetime for a worker that already acquired the old pointer. Missing/invalid requested cameras currently `continue`, returning fewer frames; callers must treat that explicitly. An async dispatcher lambda also cannot assume its continuation resumes on the engine thread after an await.

**History.** `280c939bbc742eca6c1b89d90ad3a76d3a6ec9c2` keeps the server across play/stop rather than rebuilding connections with every runtime scene. `097d8bf42fbf8e34aab5ddb106f34730529f61d8` revisits capture/step and recording boundary assumptions. Session lifetime, simulation lifetime, and observation lifetime are separate.

**Choice for Lux.** For remote tools/tests, copy the explicit owner-thread request/snapshot/completion model and define request IDs, cancellation, stale-scene rejection, and bounded queues. Prefer immutable post-step snapshots. Do not import the blocking robotics gate into ordinary gameplay/editor refresh by default. Validate simultaneous requests, disconnect during gate wait, play/stop while awaiting capture, reset before first action, and missing camera results.

### 11. Recording: excellent design questions, useful mechanisms, incomplete guarantees

**Contract.** Lucky's [RecordingIntegrity guidance](M:/LuckyEngine/MAC-Source/.claude/docs/RecordingIntegrity.md:21) demands completeness, determinism, atomic finalization, and schema fidelity. Those are stated requirements; they are not a certificate that every source path satisfies them.

**Data path.** Observer orchestrates sessions and episodes; DataRecorder samples into reusable TimeSliceBuffer batches; ParquetWriter writes Arrow columns on a worker. [Schema binding](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/RecordSourceRegistry.cpp:117) resolves source names, joint IDs, widths/types, and memory addresses outside the per-row evaluator. Tight evaluators append from already resolved fields. DataRecorder flushes batches at 50 ticks; with discard-on-failure it retains an episode's batches and submits only successful ones. This trades peak memory/latency for avoiding post-hoc numeric file removal.

**Video pipeline.** [FFmpegWriter](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Writers/FFmpegWriter.cpp:706) snapshots camera/scene payload into a slot pool, submits recording work to a render worker with per-slot command resources/fences, reads packed pixels back, and hands encoding work to a writer worker. An in-flight ring bounds GPU work; PT uses a one-slot ring because each frame is a slow multisample job. It enforces contiguous episode frame indices, latches failures, reuses payloads, and [EndEpisode](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Writers/FFmpegWriter.cpp:661) queues close after frames and waits until writes drain. NRI queue submission is serialized against presentation; device-resource access has a separate mutex. Copying this specialized immediate-render path into Lux requires proving its own NRI state and retirement rules.

**Transaction order.** [Observer::EndCurrentEpisode](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Observer.cpp:710) first closes media and waits so delayed encoder/readback failures become visible, combines HadError flags, and only then finalizes numeric/Hub episode data. September hardening unified StopSession with the same open-transaction finalization path. [Parquet worker](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Writers/ParquetDataWriter.cpp:504) closes its current file before writing episode metadata and info.json. This ordering is useful, but no crash-injection/fsync/atomic-directory-rename audit was performed. Do not claim guaranteed power-loss atomicity from it.

**Concrete integrity gap found in source.** [DataRecorder::OnUpdate](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/DataRecorder.cpp:108) calls GetFreeBuffer. If none is available it warns, sleeps 1 ms, and **returns without recording a row**. [Observer::OnUpdateData](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Observer.cpp:398) nevertheless increments CurrentDataFrameIndex and simulation recording time. [GetFreeBuffer](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Writers/ParquetDataWriter.cpp:1356) returns null for an empty three-buffer streaming pool. Thus the comment “stalling physics” is not the actual behavior: only that callback sleeps; the scheduler and row counter can advance without the row. This branch needs a slow-writer/backpressure reproduction; it is a source-supported completeness risk and should not be imported as correct backpressure. A correct no-drop path must wait/retry the same sample, fail the episode, or record a documented gap.

**Determinism is qualified.** Per-camera DLRR is opt-in and metadata marks neural_denoise/bit_reproducible false because results vary with hardware/driver/SDK. Stable callback/column ordering, seeded simulation, and integer timestamps are valuable, but do not make neural temporal processing or platform FP byte identical. The user's removed Lux temporal implementation was poor and is not a present priority; studying recording options does not authorize reintroducing temporal rendering.

**History.** `0c61769ba` introduced threaded data writing in January; `54f5eb05a` added custom schemas; `c6aba6c99f7abf8c08a315ac759894a8ae5979ff` fixed binding/types/schema tests; `3ee455ef1` added sub-frame motion interpolation for offline recording; `097d8bf42...` hardened failure paths. These changes show an evolving product, not a uniformly completed system.

**Lux choice.** The strongest reuse is a test/capture contract: simulation sample ID, render sample ID, frame count, timestamps/units, explicit row schema, terminal corruption state, bounded resources, and close-before-publish. Start with deterministic regression capture/replay for Lux before importing robotics dataset formats, Arrow/Parquet, or the complete recording UI. Force disk/encoder/queue failures and verify no nominally successful output hides missing frames.

### 12. Audio: inspect thread ownership, keep Lux's current backend

Lucky uses MiniAudio/JPL, a dedicated audio thread, source/event management and optional spatial/sound-graph work. [AudioSceneSubsystem](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Audio/AudioScene.cpp:66) collects world-space source positions/parameters into vectors and moves batches to the audio engine, initializes the listener before play-on-awake, and uses a scene-owned concurrent queue for finished one-shot entities that must be destroyed on the game thread. ### 13. Agent, auth, and Hub: reuse boundaries, reject product coupling

**Agent architecture.** LuckyEditor-Agent is a separate library depending on [IEditorAgentHost](M:/LuckyEngine/MAC-Source/LuckyEditor-Agent/include/LuckyEditorAgent/IEditorAgentHost.h:23). Main-thread queries/mutations pass through the host; scene edits go through ExecuteSceneMutation with the relevant scene's undo stack, rejecting absent/inactive/runtime scenes. [ToolRegistry](M:/LuckyEngine/MAC-Source/LuckyEditor-Agent/src/LuckyEditorAgent/LLM/ToolRegistry.h:37) stores schema+handler together, supports typed schema emitters, marks blocking heavy tools for worker dispatch, validates configured path arguments, and caches its advertised schema. **Choice for Lux.** An editor host interface with owner-thread dispatch and undo-aware mutations is directly useful if Lux gains in-editor agent tools or a test harness. Keep tool schema and validation close to the implementation. Require active scene identity at execution time, not just when the background request began. Do not copy Lucky's cloud identity, CLI assumptions, endpoint names, or tool-result privilege/steering policy without designing Lux's own trust boundary.

**Auth/HTTP method.** [AuthService](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Auth/AuthService.h:22) is application-owned, uses OAuth code/PKCE helpers, atomic flow state and mutex-protected token/flow fields, exchange/user-info workers, and a main-thread polled deep-link queue. [HubHttpClient](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Hub/HubHttpClient.cpp:24) centralizes request timeouts, auth headers, JSON headers, SSL setup and one refresh/retry on 401; extra headers strip CR/LF. **Recording is coupled to the product.** [Observer::StartSession](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Observer.cpp:236) requests Hub task approval before starting local recording. [EpisodeReportStreamer](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/EpisodeReportStreamer.h:20) uses a worker, capacity-eight queue, producer backpressure, a 30-second push deadline, stop/drain, and terminal auth/quota/payment/permission statuses that can stop the session. Transient network errors are handled differently. Those are account/billing/product rules, not fundamental rendering or recording requirements. **Choice.** Keep Lux's local engine functionality independent of LuckyHub approval and robotics accounts. If Lux later needs online features, define a separable service adapter with explicit local failure/offline policy. The reusable pieces are bounded worker queues, typed terminal outcomes, asynchronous UI state, and deterministic local output before optional upload. ### 15. Sensors: metric depth, approximate masks, LiDAR, and replay

This is a focused follow-up into actual sensor source and selected failure patches. The useful lesson for Lux is the measurement/coordinate/timing contract, not adding robotics dependencies without a product need. No claim about a missing Lux sensor is inferred from an absent filename; current Lux sensor equivalents were not inventoried here.

#### Depth and RGBD: specify what each pixel measures

[RecordPackDepth](M:/LuckyEngine/MAC-Source/LuckyEditor/Resources/Shaders/PostProcessing/RecordPackDepth.glsl:7) reads a depth-plane SRV containing reverse-Z [0,1] values. It reconstructs **positive camera-axis eye depth**, using `mul/(add-screenDepth)` for perspective or `mul*screenDepth+add` for orthographic projection. This is axial depth, not Euclidean distance along each pixel ray. It rounds metres/DepthScale and saturates to uint16, packing two adjacent row-major pixels into each uint32 for gray16le output. Default scale 0.001 means millimetre codes with a 65.535 m ceiling; quantization error and saturation are separate from camera near/far limits. Odd pixel counts use a padded final word. Clean depth does not explicitly turn a cleared background depth into a no-return sentinel; its reconstructed far/background value follows the projection/quantization path. Consumers must not silently equate it to the sensor-model zero-invalid contract.

[RecordPackDepthSensor](M:/LuckyEngine/MAC-Source/LuckyEditor/Resources/Shaders/PostProcessing/RecordPackDepthSensor.glsl:109) adds an approximation to a depth camera before quantization: raw-zero background rejection; metric near/max-range gates; incidence from decoded view normals; authored NIR or visible-albedo fallback reflectance; microfacet return/dropout; up to 24 horizontal samples for a one-sided stereo occlusion shadow; and Gaussian noise applied in disparity space (`focalPixels*baselineMetres/z`), quantized to 1/8 pixel, creating roughly z² depth noise. Structured-light mode samples a 2×2-coarser grid. iToF and sparse dToF currently fall through to ActiveStereo, **not distinct completed sensor models**. [DepthSensorModel::All](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/DataTypes.h:454) is explicitly disabled and maps to one ActiveStereo writer because concurrent model writers raced shared render-command resources. An enum is not proof all implementations work.

Transparent surfaces use an auxiliary NIR render target to attenuate the opaque return behind the pane/medium, or report the stronger front glint; this is a screen-space, limited-layer approximation, not calibrated multipath transport. The incidence term uses `abs(nView.z)` rather than the dot product with each off-axis perspective pixel ray, another approximation to check toward image corners. Visible color is only a proxy for 905 nm reflectance when authored data is absent. Noise hashes are seeded per pixel/frame, but shader transcendental/floating-point behavior does not establish cross-GPU byte identity. Diagnostic modes deliberately replace range with internal terms, so diagnostic files must not be consumed as ordinary depth.

**Ownership/cost.** [FFmpeg depth packing](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Writers/FFmpegWriter.cpp:1317) uses the captured recording camera's FOV/projection constants and frame index, GPU packs directly into HOST_READBACK storage, then the existing fence/ring/encoder pipeline writes lossless FFV1 gray16le in Matroska. RGB and depth are separate writers and render work; [CameraRecorder](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/CameraRecorder.cpp:270) waits for **all** RGB/mask/depth backlogs, then issues the same video-frame index to each. This provides a frame-boundary contract, but does not prove physically synchronized multiple real imagers. [gRPC CaptureDepth](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Grpc/GrpcCapturePool.cpp:274) instead uses cached per-view resources plus a one-shot compute command buffer, state restoration, graphics QueueWaitIdle, and a host copy; this blocks GPU work and is not an asynchronous sensor stream.

**History explains two different empty-RGBD failures.** `1179394f2069de531027f07a97769204265eb972` waits for both encoders to close before remuxing; merely queueing CloseFile left half-written inputs. `162fdf7f4ad7b750ea5a402ce30c5022f431d1c0` then replaces shell command invocation with direct ProcessHelper execution because Windows quote stripping broke paths containing spaces. HEAD pairs streams by camera name, not vector position, because DepthOnly cameras change list lengths. RGBD means two already encoded video tracks remuxed with stream copy; it is not a color/depth calibration or registration algorithm. Remux errors are logged and skipped; inspect downstream requirements before promising that an RGBD derivative is part of the same atomic success condition as the base streams.

#### Masks: this writer is an approximate target-box generator

[MaskImageWriter::Init](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Writers/MaskImageWriter.cpp:103) specifically caches entities tagged `Red Block` or `Dropbox`, with hardcoded half-extents. [WriteFrame](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Writers/MaskImageWriter.cpp:419) snapshots camera ViewProjection and target positions/extents; a CPU worker [projects eight AABB corners](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Writers/MaskImageWriter.cpp:729), bounds/clamps a screen rectangle, optionally applies deterministic size jitter, and fills it white on a black RGB image. It does not rasterize object triangles, depth-test occlusion, or assign per-instance/class labels. Skipping corners with clip.w≤0 also is not proper near-plane polygon clipping. Lossy H.264/yuv420p output is unsuitable for an exact integer label map. It must not be advertised as a general semantic/instance segmentation ground-truth system merely because its output folder says masks. Other segmentation implementations outside this writer were not exhaustively ruled out.

The worthwhile mechanism is its bounded queued-frame count, contiguous-index validation, immutable frame payload, producer mutex preventing close/frame reordering, terminal failure state, and close-before-temp-file-rename publication. Those correctness methods can transfer independently of the highly specific box-mask algorithm.

#### LiDAR: clean collision geometry first, material augmentation separately

[BuildLidarBeamDirs](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/LidarScan.h:16) defines local +X forward and +Z up, with flat index `bin*channels+channel`. Uniform spinning uses azimuth/elevation cells; Livox uses a golden-angle rosette **approximation** whose flat order is emission order, not an elevation channel image. [LidarRecorder::OnUpdate](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/LidarRecorder.cpp:351) selects a slice from RotationHz×dt, transforms it by current body/site pose and mount offset, and calls MuJoCo mj_multiRay for first-hit geometry/normals. MuJoCo coordinates are converted to engine Y-up with the scene axis transform plus root translation for live preview. Recorded normals are rotated back into sensor coordinates, while recorded range is radial metres. Every ray in that tick receives the same episode-relative timestamp and current pose; emission is rounded up and capped at one cycle per callback. This is not per-beam continuous-time motion distortion or exact pulse scheduling across arbitrary dt/rotation rates.

**Optimization and tradeoff.** Beam/ray/normal/ID scratch arrays are reused, and mj_multiRay amortizes broad-phase traversal over the scan. Mount/robot self-ignore and geometry-group filters avoid unwanted hits. Optional pass-through/reflection geometry needs extra mj_ray traversals, so a per-model/per-geom material mask restricts secondary casts to surfaces that can use them; stepped continuation is bounded. Extra secondary distances/normals are columns attached to the primary ray, not new primary rows that replay would mistakenly augment again. Data remains a clean collision scan; material noise/returns are evaluated for preview or exported variants.

[LidarParquetWriter](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Writers/LidarParquetWriter.cpp:194) writes timestamp, bin/channel, radial range, geom ID, hit flag and sensor-frame normals, with -1 range on miss and optional secondary columns. It wraps reusable vectors into Arrow arrays and flushes 16,384-row groups using ZSTD level 1, Snappy, or uncompressed fallback. **This writer flushes from the caller path; it is not the DataRecorder background writer.** Synchronous disk/compression and optional FFmpeg proxy writes can therefore cost simulation time. [CloseFile](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Writers/LidarParquetWriter.cpp:564) closes before promoting `.parquet.tmp`, removes corrupt temporary output and orphan sidecars/proxies, and marks failures. This is a useful publication boundary, not proof of fsync/power-loss atomicity across the whole file trio. The colored proxy is only a visualization; `5828885951c13a9d5d81315f6811e9e5f6e3c953` fixed a Livox emission-index array being treated as spatial image axes and introduced real azimuth/elevation projection plus viewable size bounds.

#### Replay/material bridge: identity and calibration are separate from geometry

[LidarReplayPanel](M:/LuckyEngine/MAC-Source/LuckyEditor/src/Panels/LidarReplayPanel.cpp:1251) loads and sorts episode rays, rebuilds the same beam table, bounds a playhead window with binary searches, and caps displayed points. It loads a pose timeline from recorded state and [samples nearest-earlier pose](M:/LuckyEngine/MAC-Source/LuckyEditor/src/Panels/LidarReplayPanel.cpp:1641), not interpolated motion. Pose reconstruction is explicitly a single-body MVP using the first free joint, with live body/site transforms as fallback. It does not guarantee arbitrary moving multi-body sensor rigs replay exactly. `8190a26e657f13058a675cfae5a444f75ae6fea2` fixes cross-episode pose bleed by filtering the global episode_index column instead of chunk-local filenames, and changes pose selection to upper_bound/previous. This is an identity/time lookup failure, not a raycast error.

[MaterialVoxelBake](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Lidar/MaterialVoxelBake.cpp:298) bridges collision geom hits to visual NIR materials by surface-sampling visual triangles at ≤half-cell spacing, storing textured reflectance/roughness/metalness/continuation data in a dense position-keyed voxel grid. The max-axis dimension grows effective cell size to bound memory; direct samples outrank dilated splats, ties overwrite. A geom-material table is preferred for recorded secondary hits where cell quantization would confuse shallow water with the bottom, but must be suppressed when recording and edit-time MuJoCo ID spaces differ. Material fingerprints and saved build parameters/version detect some stale bakes; transforms are deliberately excluded, so this is not full moving-scene identity/coverage validation. Dense memory, bake cost, thin surfaces, overlap, quantization and mismatched visual/collision shapes remain limitations.

[LidarReturnModel](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Lidar/LidarReturnModel.h:23) combines reflectivity/range attenuation, microfacet incidence, dropout, range noise, transmission/reflection continuations and echo limits. Replay export snapshots parameters, seeds variants, processes batches across frames, reports losses by cause, and writes model/bake/provenance metadata. These are motivated approximations with a calibration interface; inline citations and manufacturer preset names do not establish sensor validation. Bake misses preserve geometry with explicit unknown-material sentinels instead of silently changing the point distribution.

**Lux decision/validation.** Reuse explicit unit/basis/projection contracts, common capture/replay beam definitions, owned snapshots, immutable augmentation inputs, terminal failures, and truthful distinction between clean geometry and sensor artifacts. Avoid importing the robotics stack solely for these lessons. ## Reflection, crash recovery, services, and browser code

### Input and window interaction: preserve the coordinate and state contract

Lucky's [Input](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/Input.h:59) is application-owned. GLFW callbacks update key/button state and cached logical cursor position; frame transitions distinguish pressed/held/released. [Controller polling](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/Input.cpp:20) applies a per-axis threshold deadzone to raw joystick axes. This is a simpler input layer than an action-mapping system; wrapper instance ownership does not itself provide semantic bindings or deterministic input replay.

The interesting platform work is in [GLFWWindow mouse handling](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Platform/GLFW/GLFWWindow.cpp:435). At the start of a drag it latches the effective logical window size so a DPI/viewport change does not change the coordinate scale mid-drag. Cursor mode changes zero the next delta so recentering is not interpreted as user motion. On Windows a release callback checks the physical button state to suppress GLFW's synthetic focus-loss release while tearing out a viewport. These are specific interactions between OS events, ImGui viewports, editor camera/gizmos, and logical/framebuffer coordinates. History `f19660853` addresses remote/Parsec interaction rather than merely adding another cursor mode.

Current [Lux Input.cpp](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Core/Input.cpp#L33) already adds radial stick deadzones, normalized gamepad state, controller-family detection and output/haptic handling beyond raw joystick polling. Preserve those capabilities. Borrow Lucky's exact DPI/cursor-mode/drag scenarios as tests before choosing any input refactor. Platform-specific suppression needs checks with Alt-Tab, physical release outside the window, modal dialogs, remote input, high-DPI monitor changes and multi-viewport tear-out; a fix for one backend is not a universal rule.

Lucky's [ShortcutsPanel](M:/LuckyEngine/MAC-Source/LuckyEditor/src/Panels/ShortcutsPanel.cpp:274) displays manually authored chord/action rows, not a live generated keybinding registry. Lux already has a command palette/registered editor commands and keybinding documentation. A Lux learning panel should derive shortcut labels from the real command definitions where possible rather than creating another hardcoded list that can drift. This complements the contextual documentation design above.

### Deferred events: tag work with its owner, distinguish timeout from cancellation

[EventBus.h](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/EventBus.h:22) centralizes main-thread event dispatch and worker-to-main operations. Each `EventDispatcher` gets a monotonically unique owner ID. Queued work is tagged with that ID; dispatcher destruction retires the ID, and draining discards not-yet-run work from retired owners. Deferred events can remain unready until their backing state is published. A blocked owner holds back only its own FIFO tail, allowing other owners' ready operations to proceed. Callables are removed under lock and executed unlocked so they can reenter the bus. `289111e34` explains the split from one undifferentiated bus to per-owner dispatcher handles.

This is useful for project/asset jobs that can outlive the UI context that initiated them. It is not a complete concurrent object-lifetime proof: retirement does not cancel an operation already removed for execution, the bus must outlive dispatcher handles, and borrowed captures still require correct owner-thread/lifetime discipline. The shown deque scans and interior erases can be expensive under a large blocked queue; retired IDs are retained, and no generic queue-capacity/backpressure policy appears in this class.

The [blocking worker API](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/EventBus.h:204) waits at most 30 seconds and returns an empty string on timeout, but it does **not** remove/cancel the queued operation. A timed-out mutation may therefore run later. Also, erasing the queued callable destroys its captured promise; an already-waiting `future.get()` can receive broken-promise rather than the comment's promised empty result. These are source-level API semantics to test, not reproduced application failures.

**Lux choice.** The transferable design is explicit owner identity, readiness after state publication, and owner-thread execution. If Lux adds a shared dispatcher/tool API, use typed completed/cancelled/failed/timed-out outcomes and define whether cancellation suppresses side effects before they start. Validate owner destruction, delayed readiness without blocking unrelated work, reentrancy, queue pressure, timeout followed by draining, and shutdown. Do not assume a timeout makes later execution impossible.

### Native reflection: generic tools through registered type operations

**Problem.** A new editable native asset type normally requires separate type-specific inspector and serialization work. Compile-time access to known members is not the same as being able to discover and construct a type by name at runtime.

Lucky's [TypeRegistry](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Reflection/TypeRegistry.cpp:119) registers named modules. The first pass allocates every type and publishes both resolved/unresolved names; the second resolves references between types and records constructors, destructors, copy operations, member variables/functions, enums, and vector operations. Creating all types first avoids depending on declaration order within a module. `BoxedObject` and member metadata allow a generic inspector to reference the real object rather than copying every field into a UI model.

The [reflected asset editor](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Editor/ReflectedAssetEditor.cpp:295) walks structures and vectors and dispatches primitive/enum/property widgets. Its changed result drives persistence. [TypeSerializer](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Reflection/TypeSerializer.cpp:10) recursively writes primitive values, vectors, and named structures; [asset serializers](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/AssetSerializer.cpp:1792) connect this to loose files and runtime packs. This is an actual generic asset path, not proof that all existing scene components use this new reflection system.

Current [Lux TypeDescriptor](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Reflection/TypeDescriptor.h#L150) provides compile-time member access, names, variants, and type operations. That has different costs and can remain appropriate for known types. Lucky's runtime registry is useful if Lux repeatedly adds custom native data assets and wants one extensible editor/serialization path. It should not replace Lux's existing scene schema or managed reflection merely to add another reflection layer.

**Costs and limits.** Registration allocates metadata and stores pointers whose lifetime is tied to the registry. The editor currently asserts zero offset to its reflected base type, so arbitrary inheritance layout is not supported by that path. Registration holds an exclusive mutex, but `FindTypeByName`/other reads do not acquire shared locks: the presence of `shared_mutex` does not prove concurrent registration/read safety. Define a frozen-after-startup or externally synchronized registry contract before adapting it. Generic serialization still needs compatibility policy, unknown-field handling, migrations, and stable type identity; member enumeration alone does not provide them. Lux now uses rapidyaml, so Lucky's yaml-cpp emitter code is not a drop-in backend.

**Historical repair.** `dfba554d5` explicitly calls `PopAllLayers()` before `DeInitRegistry()` in Application destruction, fixing reflected metadata disappearing while layer/asset cleanup still needed it. The lesson is dependency order, not the mere addition of `DeInit`.

**Choice and verification.** Research a small registered data-asset prototype only when a real repeated inspector/serializer burden appears. Verify vectors, enum/flag edits, nested values, derived assets, save/load equivalence, old-file migration, and teardown while editors still hold references. Keep the existing compile-time path for cases where it is sufficient.

### Crash recovery: put the observer outside the failing editor

**Problem.** Once the editor is hung, GPU-lost, out of memory, or handling a fatal signal, its own UI and allocators are poor tools for producing a useful report. A same-process log alone cannot observe a dead process.

Lucky runs a [parent watchdog](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/CrashReporter/CrashReporter.cpp:1) and an editor child, with Crashpad handling dumps. Two inherited pipes carry compact event bytes: crash, manual dump, heartbeat, acknowledgement, shutdown, and parent-triggered dump requests. A screenshot-completion wakeup coordinates evidence capture before the child proceeds with dump/teardown. Parent waits use OS handles with bounded polling rather than spinning; child-exit detection is checked before deciding a missing heartbeat means a hang. The watchdog stops its own memory telemetry so its RSS does not obscure the failing child's memory history. A reduced crash-dialog application avoids initializing unrelated scene/physics/script/audio systems.

The portable abstraction is valuable: a reporter that survives its subject, explicit IPC, and a deliberately small report UI. That can complement Lux's logs/GPU diagnostics and make engine development more productive. The current Lux tree inspected here does not expose an equivalent general watchdog package; that is a tree/source observation, not proof every downstream launcher lacks one.

**Important development-snapshot compromise.** [CrashReporterClient destruction](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/CrashReporter/CrashReporterClient.cpp:115) detaches a thread blocked on a pipe and intentionally releases/leaks its implementation rather than closing/joining. The worker captures `this` and [accesses members in its read loop](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/CrashReporter/CrashReporterClient.cpp:356). This is a shutdown/lifetime concern requiring process-lifetime assumptions and validation; leaking the implementation alone is not a general proof that the owning object remains valid. Do not transplant this as reusable RAII shutdown code.

**Choice and verification.** A watchdog is a useful later tooling project after current correctness/measurement work. Reuse the process boundary and minimal IPC ideas, then design an interruptible worker shutdown and explicit evidence/error states for Lux. Exercise fatal CPU exception, deliberate hang, normal exit, child OOM/kill, parent exit, unavailable dump handler, screenshot timeout, and no-network operation. Report submission is separate from evidence collection; this study performed neither.

### Auth and Hub: isolate service coupling from local engine capabilities

Lucky's [AuthService](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Auth/AuthService.h:19) is application-owned, with explicit storage/window dependencies, atomic public auth state, locked flow/token state, browser/deep-link login and background exchanges. Normal callback flow tracks PKCE/state. The manual-code path explicitly skips state validation because of a Hub protocol difference; that is a product-specific exception, not a reusable authentication recommendation. No user token files were read during this study.

[HubHttpClient](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Hub/HubHttpClient.cpp:23) centralizes JSON requests, bounded connect/overall timeouts, header newline filtering, and one token-refresh retry after 401. These are synchronous HTTP functions: a worker call site is required to avoid blocking a frame. Distinguish client mechanics from external Hub availability, server policy, and credentials. Recording/content integrations elsewhere in this report have real Hub dependencies even when their local worker code looks self-contained.

There are details to improve before reusing the client. Its [file-write callback](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Hub/HubHttpClient.cpp:15) returns the requested byte count without checking stream failure; a successful transport result alone does not prove a download reached disk. A Lux downloader would need checked writes, temporary-file publication, cancellation, and trustworthy completion reporting. Redirect and retry policy must fit the particular service rather than copying constants.

**Choice.** Extract the explicit service ownership, worker/result handoff, error handling, and atomic-publication principles when Lux needs remote content. There is no evidence that Lux needs accounts, a Hub, or account-gated local authoring to benefit from Lucky's documentation/editor methods. Tests would simulate offline/DNS failures, expiry, rejected refresh, disk full, cancellation, and shutdown rather than relying on a live service.

### Browser code: a focused simulation target, not a native-engine web exporter

`wasm-project.md` proposes broad goals. The actual [wasm CMake target](M:/LuckyEngine/MAC-Source/wasm/CMakeLists.txt:88) compiles `WasmMain.cpp` and links `mujoco_wasm`; it does not link the native Hazel renderer, editor, asset system, or managed runtime. The [C API](M:/LuckyEngine/MAC-Source/wasm/src/WasmMain.cpp:1) owns a MuJoCo model/data pair, stepping, flat action/observation buffers, episode data, and Welford running statistics. A [web worker](M:/LuckyEngine/MAC-Source/wasm/js/simulation-worker.js:1) separates simulation work from UI messages; [data export](M:/LuckyEngine/MAC-Source/wasm/js/data-export.js:24) copies typed arrays out of the WASM heap so later heap growth does not invalidate them. [IndexedDB storage](M:/LuckyEngine/MAC-Source/wasm/js/storage.js:1) stores sessions/episodes, with download/export helpers and browser test files alongside it.

This is a useful example of narrowing a browser product to a small native kernel with an explicit API and independent presentation/storage. It is not evidence that Lucky can export a normal native game scene or that Lux could gain web rendering by copying this directory. Dataset-format comments and tests were inspected statically; compatibility and browser performance were not reproduced.

**Choice.** Preserve as an architectural reference for a future browser playground or documentation demo. For Lux, a tiny reproducible example/tutorial could justify a separate portable kernel, but a game-runtime web target would require its own renderer, shader, assets, threading, scripting, and packaging strategy. It is outside the present adaptation priorities.

### A practical first sequence

First make two narrow changes reviewable on their own: a bounded render-command submission design, and a shared-node import fixture that demonstrates all placements reaching the retained renderer.
