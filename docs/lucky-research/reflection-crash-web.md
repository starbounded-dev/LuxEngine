# Reflection, crash recovery, services, and browser code

These complementary areas were inspected separately from the renderer/content/runtime chapters. They illustrate useful methods and also why a development snapshot cannot be treated as a universally finished reference.

## Input and window interaction: preserve the coordinate and state contract

Lucky's [Input](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/Input.h:59) is application-owned. GLFW callbacks update key/button state and cached logical cursor position; frame transitions distinguish pressed/held/released. [Controller polling](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/Input.cpp:20) applies a per-axis threshold deadzone to raw joystick axes. This is a simpler input layer than an action-mapping system; wrapper instance ownership does not itself provide semantic bindings or deterministic input replay.

The interesting platform work is in [GLFWWindow mouse handling](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Platform/GLFW/GLFWWindow.cpp:435). At the start of a drag it latches the effective logical window size so a DPI/viewport change does not change the coordinate scale mid-drag. Cursor mode changes zero the next delta so recentering is not interpreted as user motion. On Windows a release callback checks the physical button state to suppress GLFW's synthetic focus-loss release while tearing out a viewport. These are specific interactions between OS events, ImGui viewports, editor camera/gizmos, and logical/framebuffer coordinates. History `f19660853` addresses remote/Parsec interaction rather than merely adding another cursor mode.

Current [Lux Input.cpp](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Core/Input.cpp#L33) already adds radial stick deadzones, normalized gamepad state, controller-family detection and output/haptic handling beyond raw joystick polling. Preserve those capabilities. Borrow Lucky's exact DPI/cursor-mode/drag scenarios as tests before choosing any input refactor. Platform-specific suppression needs checks with Alt-Tab, physical release outside the window, modal dialogs, remote input, high-DPI monitor changes and multi-viewport tear-out; a fix for one backend is not a universal rule.

Lucky's [ShortcutsPanel](M:/LuckyEngine/MAC-Source/LuckyEditor/src/Panels/ShortcutsPanel.cpp:274) displays manually authored chord/action rows, not a live generated keybinding registry. Lux already has a command palette/registered editor commands and keybinding documentation. A Lux learning panel should derive shortcut labels from the real command definitions where possible rather than creating another hardcoded list that can drift. This complements the contextual documentation design above.

## Deferred events: tag work with its owner, distinguish timeout from cancellation

[EventBus.h](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/EventBus.h:22) centralizes main-thread event dispatch and worker-to-main operations. Each `EventDispatcher` gets a monotonically unique owner ID. Queued work is tagged with that ID; dispatcher destruction retires the ID, and draining discards not-yet-run work from retired owners. Deferred events can remain unready until their backing state is published. A blocked owner holds back only its own FIFO tail, allowing other owners' ready operations to proceed. Callables are removed under lock and executed unlocked so they can reenter the bus. `289111e34` explains the split from one undifferentiated bus to per-owner dispatcher handles.

This is useful for project/asset jobs that can outlive the UI context that initiated them. It is not a complete concurrent object-lifetime proof: retirement does not cancel an operation already removed for execution, the bus must outlive dispatcher handles, and borrowed captures still require correct owner-thread/lifetime discipline. The shown deque scans and interior erases can be expensive under a large blocked queue; retired IDs are retained, and no generic queue-capacity/backpressure policy appears in this class.

The [blocking worker API](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/EventBus.h:204) waits at most 30 seconds and returns an empty string on timeout, but it does **not** remove/cancel the queued operation. A timed-out mutation may therefore run later. Also, erasing the queued callable destroys its captured promise; an already-waiting `future.get()` can receive broken-promise rather than the comment's promised empty result. These are source-level API semantics to test, not reproduced application failures.

**Lux choice.** The transferable design is explicit owner identity, readiness after state publication, and owner-thread execution. If Lux adds a shared dispatcher/tool API, use typed completed/cancelled/failed/timed-out outcomes and define whether cancellation suppresses side effects before they start. Validate owner destruction, delayed readiness without blocking unrelated work, reentrancy, queue pressure, timeout followed by draining, and shutdown. Do not assume a timeout makes later execution impossible.

## Native reflection: generic tools through registered type operations

**Problem.** A new editable native asset type normally requires separate type-specific inspector and serialization work. Compile-time access to known members is not the same as being able to discover and construct a type by name at runtime.

Lucky's [TypeRegistry](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Reflection/TypeRegistry.cpp:119) registers named modules. The first pass allocates every type and publishes both resolved/unresolved names; the second resolves references between types and records constructors, destructors, copy operations, member variables/functions, enums, and vector operations. Creating all types first avoids depending on declaration order within a module. `BoxedObject` and member metadata allow a generic inspector to reference the real object rather than copying every field into a UI model.

The [reflected asset editor](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Editor/ReflectedAssetEditor.cpp:295) walks structures and vectors and dispatches primitive/enum/property widgets. Its changed result drives persistence. [TypeSerializer](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Reflection/TypeSerializer.cpp:10) recursively writes primitive values, vectors, and named structures; [asset serializers](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/AssetSerializer.cpp:1792) connect this to loose files and runtime packs. This is an actual generic asset path, not proof that all existing scene components use this new reflection system.

Current [Lux TypeDescriptor](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Reflection/TypeDescriptor.h#L150) provides compile-time member access, names, variants, and type operations. That has different costs and can remain appropriate for known types. Lucky's runtime registry is useful if Lux repeatedly adds custom native data assets and wants one extensible editor/serialization path. It should not replace Lux's existing scene schema or managed reflection merely to add another reflection layer.

**Costs and limits.** Registration allocates metadata and stores pointers whose lifetime is tied to the registry. The editor currently asserts zero offset to its reflected base type, so arbitrary inheritance layout is not supported by that path. Registration holds an exclusive mutex, but `FindTypeByName`/other reads do not acquire shared locks: the presence of `shared_mutex` does not prove concurrent registration/read safety. Define a frozen-after-startup or externally synchronized registry contract before adapting it. Generic serialization still needs compatibility policy, unknown-field handling, migrations, and stable type identity; member enumeration alone does not provide them. Lux now uses rapidyaml, so Lucky's yaml-cpp emitter code is not a drop-in backend.

**Historical repair.** `dfba554d5` explicitly calls `PopAllLayers()` before `DeInitRegistry()` in Application destruction, fixing reflected metadata disappearing while layer/asset cleanup still needed it. The lesson is dependency order, not the mere addition of `DeInit`.

**Choice and verification.** Research a small registered data-asset prototype only when a real repeated inspector/serializer burden appears. Verify vectors, enum/flag edits, nested values, derived assets, save/load equivalence, old-file migration, and teardown while editors still hold references. Keep the existing compile-time path for cases where it is sufficient.

## Crash recovery: put the observer outside the failing editor

**Problem.** Once the editor is hung, GPU-lost, out of memory, or handling a fatal signal, its own UI and allocators are poor tools for producing a useful report. A same-process log alone cannot observe a dead process.

Lucky runs a [parent watchdog](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/CrashReporter/CrashReporter.cpp:1) and an editor child, with Crashpad handling dumps. Two inherited pipes carry compact event bytes: crash, manual dump, heartbeat, acknowledgement, shutdown, and parent-triggered dump requests. A screenshot-completion wakeup coordinates evidence capture before the child proceeds with dump/teardown. Parent waits use OS handles with bounded polling rather than spinning; child-exit detection is checked before deciding a missing heartbeat means a hang. The watchdog stops its own memory telemetry so its RSS does not obscure the failing child's memory history. A reduced crash-dialog application avoids initializing unrelated scene/physics/script/audio systems.

The portable abstraction is valuable: a reporter that survives its subject, explicit IPC, and a deliberately small report UI. That can complement Lux's logs/GPU diagnostics and make engine development more productive. The current Lux tree inspected here does not expose an equivalent general watchdog package; that is a tree/source observation, not proof every downstream launcher lacks one.

**Important development-snapshot compromise.** [CrashReporterClient destruction](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/CrashReporter/CrashReporterClient.cpp:115) detaches a thread blocked on a pipe and intentionally releases/leaks its implementation rather than closing/joining. The worker captures `this` and [accesses members in its read loop](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/CrashReporter/CrashReporterClient.cpp:356). This is a shutdown/lifetime concern requiring process-lifetime assumptions and validation; leaking the implementation alone is not a general proof that the owning object remains valid. Do not transplant this as reusable RAII shutdown code.

**Choice and verification.** A watchdog is a useful later tooling project after current correctness/measurement work. Reuse the process boundary and minimal IPC ideas, then design an interruptible worker shutdown and explicit evidence/error states for Lux. Exercise fatal CPU exception, deliberate hang, normal exit, child OOM/kill, parent exit, unavailable dump handler, screenshot timeout, and no-network operation. Report submission is separate from evidence collection; this study performed neither.

## Auth and Hub: isolate service coupling from local engine capabilities

Lucky's [AuthService](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Auth/AuthService.h:19) is application-owned, with explicit storage/window dependencies, atomic public auth state, locked flow/token state, browser/deep-link login and background exchanges. Normal callback flow tracks PKCE/state. The manual-code path explicitly skips state validation because of a Hub protocol difference; that is a product-specific exception, not a reusable authentication recommendation. No user token files were read during this study.

[HubHttpClient](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Hub/HubHttpClient.cpp:23) centralizes JSON requests, bounded connect/overall timeouts, header newline filtering, and one token-refresh retry after 401. These are synchronous HTTP functions: a worker call site is required to avoid blocking a frame. Distinguish client mechanics from external Hub availability, server policy, and credentials. Recording/content integrations elsewhere in this report have real Hub dependencies even when their local worker code looks self-contained.

There are details to improve before reusing the client. Its [file-write callback](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Hub/HubHttpClient.cpp:15) returns the requested byte count without checking stream failure; a successful transport result alone does not prove a download reached disk. A Lux downloader would need checked writes, temporary-file publication, cancellation, and trustworthy completion reporting. Redirect and retry policy must fit the particular service rather than copying constants.

**Choice.** Extract the explicit service ownership, worker/result handoff, error handling, and atomic-publication principles when Lux needs remote content. There is no evidence that Lux needs accounts, a Hub, or account-gated local authoring to benefit from Lucky's documentation/editor methods. Tests would simulate offline/DNS failures, expiry, rejected refresh, disk full, cancellation, and shutdown rather than relying on a live service.

## Browser code: a focused simulation target, not a native-engine web exporter

`wasm-project.md` proposes broad goals. The actual [wasm CMake target](M:/LuckyEngine/MAC-Source/wasm/CMakeLists.txt:88) compiles `WasmMain.cpp` and links `mujoco_wasm`; it does not link the native Hazel renderer, editor, asset system, or managed runtime. The [C API](M:/LuckyEngine/MAC-Source/wasm/src/WasmMain.cpp:1) owns a MuJoCo model/data pair, stepping, flat action/observation buffers, episode data, and Welford running statistics. A [web worker](M:/LuckyEngine/MAC-Source/wasm/js/simulation-worker.js:1) separates simulation work from UI messages; [data export](M:/LuckyEngine/MAC-Source/wasm/js/data-export.js:24) copies typed arrays out of the WASM heap so later heap growth does not invalidate them. [IndexedDB storage](M:/LuckyEngine/MAC-Source/wasm/js/storage.js:1) stores sessions/episodes, with download/export helpers and browser test files alongside it.

This is a useful example of narrowing a browser product to a small native kernel with an explicit API and independent presentation/storage. It is not evidence that Lucky can export a normal native game scene or that Lux could gain web rendering by copying this directory. Dataset-format comments and tests were inspected statically; compatibility and browser performance were not reproduced.

**Choice.** Preserve as an architectural reference for a future browser playground or documentation demo. For Lux, a tiny reproducible example/tutorial could justify a separate portable kernel, but a game-runtime web target would require its own renderer, shader, assets, threading, scripting, and packaging strategy. It is outside the present adaptation priorities.
