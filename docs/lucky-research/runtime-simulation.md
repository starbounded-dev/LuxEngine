# LuckyEngine engineering study: runtime, ownership, simulation, scripting, animation, audio, and automation

Research date: October 23, 2026. Lucky source examined at `b9ec0f117224f3c4556340d94d827ce7d159f9e7`; Lux current source comparisons use remote `dev` at `cc25be60385cf342a61030c2b12204c226b94ffa`. The local Lux working tree is an older May snapshot and was not used to declare missing current features. Historical Hazel comparisons below mean the actual `pr-base` commit `d16adf54a` (Hazel 2024.1.1), **not today's unavailable Hazel source**. Lux is independently developed, inspired by Hazel, and is not a fork.

This chapter follows implementations and selected history patches. It is not a runtime verification, exhaustive line audit, performance benchmark, or endorsement of every method in Lucky. Repository guidance was read first; source takes precedence where architecture/threading prose has drifted. For example, Threading.md still names NVRHI and calls AuthService a singleton, while the inspected implementation uses NRI and an application-owned AuthService. No engine source, project settings, authentication, or cloud service was modified.

## 1. The most useful runtime lesson is explicit lifetime boundaries

**Problem.** A process can have multiple applications/projects/tests, while some third-party libraries only support one process-wide instance. Treating every system as a singleton hides dependencies and makes startup, project switches, headless tests, and shutdown fragile. Treating every system as independently instantiable is also wrong for CoreCLR/Jolt/JPL.

**Lucky's method.** The June lifecycle work separates three ownership levels:

1. `Application` owns its renderer/window/services and keeps the scripting host alive while projects change.
2. A `Project` owns its `ScriptEngine` and physics API/resources. `ScriptEngineContext` explicitly supplies nonowned input, time, dispatch, audio, window, and auth pointers; headless services can be null.
3. `ScriptHost::Acquire()` and `JoltCore::Acquire()` share the unavoidable process-level CoreCLR and Jolt registration state. A mutex protects acquisition and a weak reference avoids making the service immortal. Each project ScriptEngine has its own uniquely named assembly load context.

Sources: [Application service construction](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/Application.cpp:177), [ScriptEngineContext](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Script/ScriptEngineContext.h:17), [ScriptEngine constructor/destructor](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Script/ScriptEngine.cpp:25), [ScriptHost acquisition](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Script/ScriptHost.cpp:226), [JoltCore acquisition](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Physics/JoltPhysics/JoltCore.cpp:66).

**History that explains the method.** `8f5f8fed6` introduced the shared ScriptHost because CoreCLR cannot be spawned twice in a process. `c7e2865f76c76286f6b04095c0a9b2b9cc58088b` moved ScriptEngine to each project and reworked destruction ownership. `9cbf8cdf86cd61e12da766ca8b9fc1e56a0a1c38` extracted Jolt registration into JoltCore so multiple JoltAPI instances could coexist. `ced9b4610` then made actual Project/Scene construction usable in windowless engine tests. These are related problem/solution steps, not independent feature additions.

**Limits.** The refactor does not establish arbitrary multi-world execution: `JoltScene` still has `s_CurrentInstance` and explicitly rejects a second physics scene; `GrpcStepSystem` has a single active runtime scene pointer; several script glue component maps remain process-level. A dependency pointer bag requires its owner to outlive every borrower. Do not infer isolation from the existence of per-project objects.

**Compared with Lux.** Current [Lux ScriptEngine](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Scripting/ScriptEngine.cpp#L67) is one process singleton holding the host, load context, current scene, metadata, and managed handles. Current [Lux PhysicsSystem](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Physics/PhysicsSystem.cpp#L56) similarly keeps global registration/resources. This is a simpler design for one active project, not evidence it is automatically wrong. Lucky's separation becomes valuable for concurrent previews, isolated headless tests, multiple project lifetimes, or independent subsystem startup. A focused Lux adaptation would separate process host lifetime from project script lifetime first, rather than blindly replacing all singletons.

**Verification needed before choosing.** Repeated project open/close, multiple engine fixtures within one process, script reload during scene replacement, partial initialization failures, and shutdown with worker callbacks still pending. Track live native/managed resources across the cycles. Agent-authored design explanations are hypotheses to verify, not user intent.

## 2. Weak references: learn the failure and audit the proposed fix

**Lux now.** Its [WeakRef](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Core/Ref.h#L241) stores a raw object pointer, checks a live-address registry, and exposes direct dereference and `dynamic_cast` through that pointer. `IsValid()` only answers whether that address is currently registered; it neither pins the object nor identifies an allocation generation. Deleting and reusing an address can make an old weak reference appear valid for a different object. Checking validity and then dereferencing also has a destruction window when threads are involved. Lux already uses the atomic decrement's returned value to decide final deletion, so that part should not be presented as a new missing fix.

**Lucky's change.** `19203440e8f972356a77c4c2add5d0f1deb64046` describes actual weak-reference use-after-free and final-reference races. The patch:

- Uses the returned atomic decrement to choose one deleting thread.
- Allocates a separate `WeakBlock` only when an object first acquires a weak reference. The block has its own weak count and an atomic instance pointer, and survives after the object dies.
- Clears the instance in the base destructor, and adds compare-exchange increment only when the intrusive strong count is nonzero.
- Removes direct weak dereference; callers must `Lock()` to a strong Ref before use. A queued physics synchronization now checks both the locked body and its entity.

Sources: [RefCounted/control block](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/Ref.h:13), [Lock](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/Ref.h:353), [body synchronization](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Physics/JoltPhysics/JoltScene.cpp:676). The historical Hazel baseline used the older live-address pattern.

**Cost/benefit.** The API encourages safe ownership and the separate block solves stale address identity after completed destruction. Ordinary strong-only objects avoid a separate block allocation. Weak users pay an allocation and atomic weak bookkeeping.

**Important unresolved source-level concern.** Lucky's `Lock()` loads the object pointer from the block and then calls `instance->TryIncRefCount()` on a counter **inside the object**. Another thread can release the last strong reference, run destruction, and free the object between those two operations. The separate block staying alive does not itself pin the allocation containing the strong count. The source therefore does not prove `std::weak_ptr`-equivalent concurrent safety, despite the commit's claim. This is a concrete interleaving concern, not a crash reproduced in this study; external synchronization may make particular call sites safe. A replacement should keep the strong count in independently live storage or otherwise synchronize locking against final release, and prove the invariant.

**Choice for Lux.** Investigate Lux's weak call sites and their thread/lifetime contracts. Adopt the ownership requirement (lock before use, reliable allocation identity), but do not copy this implementation as a proven concurrency fix. Tests must overlap the last strong release with repeated weak locks and force address reuse; a sequential churn test alone does not cover the interleaving.

## 3. TimeManager: multi-rate scheduling, not a generic task scheduler

**Problem.** Physics, control, sensors, dataset rows, and video can run at different frequencies. Driving each from its own float accumulator or from editor refresh can change action/observation ordering, drift timestamps, and make replay depend on rendering speed.

**Actual implementation.** [TimeManager.h](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/TimeManager.h:18) supports at most eight runner slots. It schedules Acquisition → Control → Physics → Validation → Export, plus optional free updates before and after those phases. For each deterministic event:

1. Find the smallest integer-nanosecond time until any runner is due.
2. Push precisely that interval into every active runner.
3. Capture current step durations before the push rotates a runner's fractional-period sequence.
4. Build an eight-bit due-runner mask.
5. Run the precomputed callback list for that mask in each phase, giving each callback its runner's dt and the other runners' alpha/step values.
6. Advance simulation time after the phases, so all consumers within the event see the same timestamp.

Sources: [baking callback permutations](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/TimeManager.cpp:56), [deterministic event](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/TimeManager.cpp:586), [fractional period generation](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/TimeStepRunner.hpp:145), [sync point timestamp latch](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/SyncPointSystem.cpp:12).

**Optimization.** Rebuild each phase's sorted callback arrays at registration/config changes, not every tick. There are up to 256 runner masks per phase; callbacks are flattened and stable-sorted by priority. A `FastCallback` is an instance pointer plus a function pointer, avoiding a captured `std::function` for fixed work. `PausePhaseCaching/ResumePhaseCaching` amortizes startup registration. This trades setup time and duplicated callback storage, exponential in runner count, for a small hot loop. Raising the runner limit is not free.

**Clock precision.** `set_hz` generates a repeating sequence of integer-ns durations from rounded cumulative ideal time, bounded to 32 entries; this handles common fractional-ns periods more faithfully than rounding every 30/60 Hz step the same way. It should not be described as exact rational scheduling for every possible frequency. `0af4c819e07c56a6053a32defb2d0a69394b3fac` removed a 100 ns near-coincidence merge tolerance; the actual patch matters because coalescing nearby events can alter which phases run together.

**Three modes.** Realtime non-deterministic mode can drop excess steps. Low-performance deterministic mode processes all simulation events but allows simulation to fall behind wall time; CPU/UI budgets limit how much is done per display frame. High-performance deterministic mode removes wall-time pacing and runs as many complete events as its budget permits. EMA overhead estimates influence batching/UI pacing, not the logical next-event sequence. A slow callback cannot be preempted; the budget is checked between events. Deterministic scheduling does not prove cross-platform floating-point, physics, random generator, or neural rendering determinism.

**History.** `8f4112f1ef96197b4f1836afd7814aecf8a1ddd7` introduced the initial scheduler (its subject reports an 11× speedup, not independently reproduced here). `49e3b4977` moved scene updates through it, and `f3a9de2d74309a3cb9837cb471661d0ce153489a` removed physics accumulators so there is one timing authority. `61ef4b589` added strict UI responsiveness. Reading this sequence explains why the system exists.

**Lux comparison and choice.** Current [Scene::OnUpdateRuntime](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Scene/Scene.cpp#L792) invokes script OnUpdate with frame dt, then calls StepPhysics; [PhysicsScene::Simulate](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Physics/PhysicsScene.cpp#L825) owns its accumulator/substep policy and also offers SimulateStep. For gameplay this is simpler. The valuable principle is one explicit fixed-step authority and documented ordering between scripts/controllers/physics, not necessarily all five robotics phases or all-mask caching. First test a force applied in a script at 30/60/144 display Hz, pause/single-step, root motion, and collisions before deciding if Lux needs a fixed-script hook or a larger scheduler. Keep display-rate UI/audio needs explicit.

## 4. Threads and workers: different architectures must not be conflated

LuckyEditor's [binary configuration](M:/LuckyEngine/MAC-Source/LuckyEditor/src/LuckyEditor.cpp:509) selects `ThreadingPolicy::SingleThreaded`. Render submissions are deferred on that same main thread; dedicated rendering exists in multithreaded runtime configurations. The TimeManager runner callbacks execute serially when the scene drives them; phase names do not imply worker threads. Current Lux Windows defaults to a real render thread; Linux's default differs. A Lucky main-thread shortcut cannot be transplanted into Lux without tracing that difference.

Lucky's one-shot jobs generally have a `Start` factory, a `std::jthread` declared last so it joins before borrowed members die, atomics publishing completion, locked progress, and a one-time main-thread result handoff. [ImportProjectJob](M:/LuckyEngine/MAC-Source/LuckyEditor/src/Utilities/Content/ImportProjectJob.h:22) and [its worker launch](M:/LuckyEngine/MAC-Source/LuckyEditor/src/Utilities/Content/ImportProjectJob.cpp:126) are useful concrete patterns. The guidance describes stop-token cancellation; this particular import job's actual `RunBackground()` has no stop-token parameter, so cancellation cannot be assumed just because it uses jthread.

Current [Lux JobSystem](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Core/JobSystem.h#L11) is a separate fork-join pool: workers plus caller share disjoint parallel ranges; zero-worker policy runs inline. It is already used for retained-scene transform work, and is separate from Jolt's pool and the render thread. A one-shot I/O job, a fixed-phase scheduler, and a fork-join CPU pool solve different problems. Preserve those distinctions.

**Choice.** Use explicit job lifetime/result handoff for long editor operations; use Lux's pool for bounded CPU fan-out; keep GPU submission under Lux's existing renderer contract. Validate shutdown while jobs are active and cancel only at points the implementation actually supports. A source convention such as “no GPU on workers” must be checked against real exceptions: FFmpegWriter has a recording render worker and synchronized NRI work.

## 5. Modules: optional capability negotiation and orderly teardown

**Problem.** A renderer feature such as path tracing needs optional device extensions before device creation, capability checks after device creation, feature shaders at renderer startup, and teardown before the renderer/device die. A Boolean setting inside a giant renderer cannot express all of those stages reliably.

**Method.** [Module](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/Module/Module.h:15) exposes a descriptor, named dependencies, side-effect-free requirement checks, load/background-startup hooks, renderer hooks, and polled shutdown. Checks return Pending, Unsupported, Degraded, or Supported; optional failures become visible dormant modules and required failures become startup errors. [Application](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/Application.cpp:177) evaluates in waves, lets hooks request extensions before device creation, publishes actual graphics capabilities, makes the final requirements decision, then supplies shader manifests and loads supported modules with explicit services.

**Ordering/optimization.** [Registry sorting](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/Module/ModuleRegistry.cpp:59) uses deterministic topological order with lexical tie-breaks rather than registration order. The implementation scans vectors to find dependencies and ready nodes: acceptable startup work for a small module set, not a high-throughput graph engine. Missing named dependencies warn and are ignored for ordering, so DependsOn is not a hard proof another subsystem exists. Cycles become fatal/dormant failures. Each loaded module gets a tagged HeapArena for attributable long-lived allocations; this is telemetry and ownership policy, not evidence every ordinary allocation is routed through it.

**Shutdown.** [UnloadModules](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Core/Module/ModuleRegistry.cpp:309) polls in reverse load order and only retires a module when it is done and **all later-loaded modules** are down. This conservatively orders more than direct graph dependents. It yields for 64 polls, then sleeps 1 ms and periodically warns. There is no hard timeout. Module-owned worker drains may progress; the render queue is not pumped here, so waiting for a newly queued render command can deadlock, especially in single-threaded mode. The contract explicitly requires earlier GPU flushes.

**History and limits.** `de52bfbfee59a2402d2c700b6b7735c61a2b11e9` is titled “First pass at module refactor”; it extracts the actual path-tracing implementation into `Modules/Hazel.PathTracing`. Generic comments list scripting/audio as possible modules, but that is not proof they are already modularized. The separate Hazel.Memory submodule's internals were unavailable in this checkout; only its module integration calls were inspected.

**Lux choice.** Adapt if Lux needs independently optional rendering/simulation/tool packages and capability fallback. The first unit should have a real lifecycle problem to solve. Keep Lux's NRI lifetime/synchronization approach under review rather than treating any existing agent-authored design as mandated. Do not build a plugin framework merely to imitate a directory layout. Test unsupported hardware, disabled optional module, required capability failure, repeated load/unload, and worker/GPU-drain teardown.

## 6. Jolt: same dependency, materially different integration

**Lucky flow.** Scene registers Jolt callbacks in the TimeManager phases. [Acquisition](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Physics/JoltPhysics/JoltScene.cpp:107) bulk-adds queued bodies; Control calls PreSimulate; Physics updates characters then calls `JPH::PhysicsSystem::Update(ts, 1, allocator, pool)`; Export calls PostSimulate and capture/contact work. [Bulk insertion](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Physics/JoltPhysics/JoltScene.cpp:644) uses AddBodiesPrepare/AddBodiesFinalize instead of adding every pending body separately. [PhysicsScene pre/post](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Physics/PhysicsScene.cpp:99) separates scene-to-physics transform changes from physics-to-scene updates.

**Concrete constraints.** [JoltAPI](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Physics/JoltPhysics/JoltAPI.cpp:11) reserves `300 * 1024 * 1024` bytes of scratch, despite a stale `//10 mb` comment, and constructs a pool with six worker threads. [JoltScene](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Physics/JoltPhysics/JoltScene.cpp:36) allows only one current instance and hardcodes body/pair/contact capacities. These are product/workload decisions to measure, not sensible universal defaults.

**Lux flow.** Current Lux already has Jolt bodies, colliders/cooking, queries, controllers, contact events, and fixed stepping. [Simulate](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Physics/PhysicsScene.cpp#L825) accumulates and clamps collision steps, updates Jolt, then synchronizes active bodies; SimulateStep runs one explicit step. [PhysicsSystem](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Physics/PhysicsSystem.cpp#L76) sizes its pool from hardware concurrency. Its current Simulate order calls controller PreSimulate before Jolt and controller Simulate/PostSimulate afterward, whereas Lucky's character Simulate happens before Jolt. This difference deserves controlled behavioral tests; ordering alone is not proof one controller is correct.

**Historical Hazel.** `pr-base:Hazel/src/Hazel/Physics/PhysicsScene.cpp` had a local float accumulator and SubStepStrategy. Lucky's January 2026 change removed it in favor of the shared scheduler. Lux's resemblance to the older accumulator is a method comparison, not a lineage claim.

**Choice.** Investigate bulk body creation for Lux loading/spawning and verify controller/physics ordering. Keep hardware-aware pool sizing and select scratch/capacities from observed peak requirements. For a scheduler change, choose who owns fixed timing before moving callbacks; two accumulators in series can create missed/double steps. Verify moving-platform contact, jump, kinematic motion, parented bodies, add/remove during play, and sleeping-body edits.

## 7. Coral scripting: ownership, reload, ABI, and authored data

Both engines already use Coral. Even the inspected Hazel 2024 baseline includes Coral; “adopt Coral from Lucky” is not the useful question.

**Lucky's method.** Each project owns a ScriptEngine/ALC, while the application retains the shared process ScriptHost across switches. A scene ScriptStorage gets a nonowning back-pointer; [SetCurrentScene/destructor](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Script/ScriptEngine.cpp:60) clears that pointer before engine teardown. Assembly failures reset failed AssemblyData so later type iteration does not dereference a nominally present but failed assembly. Destruction releases field defaults, unloads the ALC, runs collect/finalizers/collect, and deliberately **does not clear the process-wide Coral TypeCache** while other engines may still use its Type pointers.

[ScriptEngineScope](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Script/ScriptEngine.h:365) is a nestable RAII thread-local current-engine pointer for native glue callbacks that cannot receive a C++ context explicitly. Scope destruction restores the previous pointer. It removes a global active-project lookup but requires every managed-entry thread to have a scope; gRPC pool threads lack it, leading to specialized marshalling/registry paths. Some glue maps are still globals, so this is not full context isolation.

**Lux comparison.** Current [ReloadAppAssembly](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Scripting/ScriptEngine.cpp#L276) clears live handles and metadata, unloads its sole ALC, clears TypeCache, collects, recreates the ALC/core, and registers glue. That is coherent with one engine/ALC; copying Lucky's per-project ownership without revisiting TypeCache clearing would create dangling metadata in other engines. Lux already has shadow-copy assemblies, scene field storage and unresolved-script preservation. Those must survive any host refactor.

**Interop evidence.** [ScriptGlueHelpers](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Script/ScriptGlueHelpers.h:94) uses plain uint64 handles because wrapper UUID/AssetHandle classes do not have a reliable shared ABI. `e6ede1dff` fixes Linux Coral Boolean behavior; `6d389b850` fixes deterministic field ordering. These are valuable prompts to trace field size, signedness, array ownership, struct layout, calling convention, and declaration ordering, not just compare method names. Generated bindings and runtime reflection still need ABI tests.

**Choice.** Prioritize repeatable play/stop/reload and native-to-managed lifetime invariants; split host/project ownership only when its isolation benefit is required. Validate inherited fields, arrays, entity references, unresolved scripts, assembly failure, reload after build, and Release/Dist on supported platforms. Do not reintroduce an old missing-lifecycle claim from the May Lux snapshot.

## 8. Animation: compressed tracks, root-motion timing, and graph lifetime

**Problem.** Skeletal animation must balance memory, sampling cost, blending, root-motion continuity, asset reload, and physics timing. The asset/graph editor being present does not solve those questions.

**Pipeline.** [AssimpAnimationImporter](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/AssimpAnimationImporter.cpp:252) maps channels to skeleton indices, reserves channel zero for artificial root motion, derives missing/default tracks, and can extract selected root translation/rotation components. It transforms root motion into a common reference frame with an identity first root pose, permitting blends across clips. [Compression](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Asset/AssimpAnimationImporter.cpp:596) builds ACL QVV tracks, preprocesses, and compresses at import time. Runtime [AnimationNodes](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Animation/Nodes/AnimationNodes.cpp:65) maintains an ACL decompression context, seeks to time, and writes directly into reusable pose storage.

**Optimization and precondition.** [PoseTrackWriter](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Animation/PoseTrackWriter.h:14) skips default translation/rotation/scale subtracks because the destination pose has already been filled with the skeleton rest pose; it skips root scale and uses SIMD store helpers. That optimization is correct only if initialization/reset actually satisfies the precondition. Root-motion code separately handles forward/backward loop wrap, and time changes resample to establish the next delta baseline. Retargeting caches a bone map when clip and target skeleton differ.

**Graph mechanics/costs.** [Graph::Process](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Animation/AnimationGraph.cpp:221) traverses its node list; endpoint streams refer to graph storage, and state-machine transitions may evaluate source and destination with synchronized time scaling. This is not evidence of a SIMD job scheduler or crowd-animation batching. [AnimationGraph](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Animation/AnimationGraph.cpp:279) explicitly stores a raw Skeleton pointer to avoid repeated asset lookup/refcount traffic and notes the need to rebuild graph instances on skeleton reload. [NodeProcessor](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Animation/NodeProcessor.h:123) warns that introducing a new input into an existing graph without supplying a default can cause validation failure or a null dereference. These are concrete cache invalidation/schema-evolution costs.

**History.** ACL decompression/root motion already appear in historical Hazel `pr-base`; do not attribute all animation engineering to Lucky's later fork. `b223337ed0329675ae82b140abd0867a175fa96a` fixes “root motion not moving character” by changing animation's scheduled location so its outputs exist before physics consumes them. It edits scene settings/serialization, not the sampler: a strong example of a correct algorithm failing because its integration order was wrong.

**Lux choice and evidence limit.** A complete recursive tree of current Lux contains animation/skeleton editor icons but no dedicated animation implementation directory. Its [Mesh.h](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Renderer/Mesh.h#L270) retains bone structures/buffer access and a dynamic-mesh comment, while skeleton/animation accessors and stored skeleton/clip members are commented out. [Components.h](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Scene/Components.h#L560) retains BoneEntityIds; the current importer includes Assimp's bone-weight limit flag but no clip/skeleton processing was found in that file. These inspected paths do not establish an equivalent complete active skeletal/graph pipeline; icons and scaffolding do not prove it exists. This is a stronger bounded source finding than an absent guessed filename, but not a runtime audit of every downstream consumer. If animation work is scheduled, trace the remaining import/component/render consumers and prioritize a small complete path—import, compressed sampling, blending, root motion, skinning, reload—before inheriting Lucky's graph/editor/robot-controller coupling. Benchmark sample/decompress cost, pose bytes, compression error, animation-to-physics order, and root-motion loop/teleport behavior.

## 9. MuJoCo and robotics: valuable control/observation contracts, specialized product scope

**Why two physics integrations.** Lucky has ordinary Jolt gameplay physics and MuJoCo model/data instances for articulated robot simulation, sensors, actuators, policies, and training. Source does not establish one joint solver that automatically couples Jolt and MuJoCo bodies. Avoid presenting this as a free physics quality upgrade for Lux.

**Method.** [MujocoSceneInstance](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Physics/Mujoco/MujocoSceneInstance.h:82) owns compiled model/data, ECS mappings, buffers, visual/physics assets, and per-instance policy application. The split [Acquisition/Control/Physics](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Physics/Mujoco/MujocoSceneInstance.cpp:2982) path sets external wrenches, sanitizes state, neutralizes policy-owned actuators **before mj_step1**, computes controls/policies, applies gravity compensation as the designated force writer, calls mj_step2, and clears transient wrenches. Another mode runs exact substeps without a local accumulator; policy runtimes are ensured loaded before the first actuator-neutralization decision so episode zero matches subsequent episodes.

**Ownership is part of correctness.** [PolicyApplier](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Robots/Policy/PolicyApplier.h:22) owns runtimes per (entity, policy-slot), sorts/application-orders by priority, tracks claimed joints, and owns a session cache that outlives borrowed runtimes. It reseeds controller targets after teleport and resets policy-controlled joints outside an agent's own joint list. Otherwise the next PD control step can yank a teleported robot back or leak the previous episode's state. `Reset` explicitly clears warm-start/scratch state before full forward dynamics; kinematic refresh and simulation-ready reset are different operations.

**Optimization.** [PolicyNetwork](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Learn/PolicyNetwork.cpp:66) caches names/session configuration, uses one intra-op thread with deterministic inference requested, and runs batches into preallocated observation/action buffers. The per-instance PolicyApplier path is more scoped than the older process-global network cache, so these are related mechanisms, not one unified ownership model. No throughput claim is made here.

**Import/runtime boundary.** [MujocoVFS](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Physics/Mujoco/MujocoVFS.cpp:27) builds a MuJoCo VFS from packed file entries with bounds/error handling, normalizes its lookup names to MuJoCo's basename/lowercase semantics, and invalidates the entire VFS on a failed entry. Root scale is explicitly warned as not propagated into the MuJoCo model. Coordinate conversion, compile-time versus runtime state, multiple geometry/material sources, and asset name collisions all matter before reusing this integration.

**Choice.** For Lux, retain the transferable lessons: one writer per control quantity, explicit force/pose ownership, controller reseed on teleport, deterministic reset of hidden solver state, and preallocated batch I/O. Import MuJoCo/ONNX/training product layers only if robotics or articulated-control simulation becomes an explicit Lux goal. LuckyLab is retired and absent; LuckyRobots is a separately distributed SDK, not a vendored source tree in this checkout.

## 10. gRPC: phase-correct snapshots and a deliberately blocking action gate

**Problem.** RPC handlers run on a worker pool, while Scene/ECS/rendering are main-thread owned. Waiting for a main-thread dispatcher at the wrong moment deadlocks if the main thread is itself waiting for an external action. Capturing camera data at arbitrary editor refresh time can return a pre-action image alongside a post-action state.

**Actual Step path.** [AgentService.Step](M:/LuckyEngine/MAC-Source/Hazel-ScriptCore/Source/Hazel/Net/Grpc/Services/AgentServiceImpl.cs:140) requires a registered external AgentBatch. The handler queues camera requests, writes thread-safe external action snapshots, signals the external-action gate **before** any wait for main-thread service, then awaits an observation frame counter on the worker. It handles a reset-frame baseline to avoid consuming/skipping the wrong first observation. Tick-only Step is a gated advance for a registered agent, not an agent-free general scene step.

[ExternalActionGate](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Learn/ExternalActionGate.cpp:56) uses atomic wait/notify in Acquisition. It intentionally blocks the simulation/main thread until an action arrives. A watchdog wakes it on disconnect/timeout. Reset/stop deactivate the gate from the worker first so the main thread can drain the reset request. The watchdog invokes its timeout effect before waking the waiting thread and avoids calling its own join path. This is specialized synchronous external simulation control, not ordinary nonblocking editor work.

[GrpcStepSystem](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Grpc/GrpcStepSystem.cpp:67) consumes requests during Export, resolves cameras on the owning thread, captures color/metric depth, copies pixels into owned vectors, and signals a condition variable. [GrpcMainThreadDispatcher](M:/LuckyEngine/MAC-Source/Hazel-ScriptCore/Source/Hazel/Net/Grpc/GrpcMainThreadDispatcher.cs:105) drains up to 256 queued work items per pump; TaskCompletionSource continuations run asynchronously rather than reentering engine code inline during completion.

**Costs/limits.** Camera captures can involve render/readback stalls and a full pixel copy per result. The C++ capture state has a single pending request batch and a single ready batch, not per-request correlation; concurrent Step callers need serialization outside this object. The static active system is a nonowning atomic raw pointer. Clearing it at stop and waking waiters is useful but does not itself prove safe lifetime for a worker that already acquired the old pointer. Missing/invalid requested cameras currently `continue`, returning fewer frames; callers must treat that explicitly. An async dispatcher lambda also cannot assume its continuation resumes on the engine thread after an await.

**History.** `280c939bbc742eca6c1b89d90ad3a76d3a6ec9c2` keeps the server across play/stop rather than rebuilding connections with every runtime scene. `097d8bf42fbf8e34aab5ddb106f34730529f61d8` revisits capture/step and recording boundary assumptions. Session lifetime, simulation lifetime, and observation lifetime are separate.

**Choice for Lux.** For remote tools/tests, copy the explicit owner-thread request/snapshot/completion model and define request IDs, cancellation, stale-scene rejection, and bounded queues. Prefer immutable post-step snapshots. Do not import the blocking robotics gate into ordinary gameplay/editor refresh by default. Validate simultaneous requests, disconnect during gate wait, play/stop while awaiting capture, reset before first action, and missing camera results.

## 11. Recording: excellent design questions, useful mechanisms, incomplete guarantees

**Contract.** Lucky's [RecordingIntegrity guidance](M:/LuckyEngine/MAC-Source/.claude/docs/RecordingIntegrity.md:21) demands completeness, determinism, atomic finalization, and schema fidelity. Those are stated requirements; they are not a certificate that every source path satisfies them.

**Data path.** Observer orchestrates sessions and episodes; DataRecorder samples into reusable TimeSliceBuffer batches; ParquetWriter writes Arrow columns on a worker. [Schema binding](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/RecordSourceRegistry.cpp:117) resolves source names, joint IDs, widths/types, and memory addresses outside the per-row evaluator. Tight evaluators append from already resolved fields. DataRecorder flushes batches at 50 ticks; with discard-on-failure it retains an episode's batches and submits only successful ones. This trades peak memory/latency for avoiding post-hoc numeric file removal.

**Video pipeline.** [FFmpegWriter](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Writers/FFmpegWriter.cpp:706) snapshots camera/scene payload into a slot pool, submits recording work to a render worker with per-slot command resources/fences, reads packed pixels back, and hands encoding work to a writer worker. An in-flight ring bounds GPU work; PT uses a one-slot ring because each frame is a slow multisample job. It enforces contiguous episode frame indices, latches failures, reuses payloads, and [EndEpisode](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Writers/FFmpegWriter.cpp:661) queues close after frames and waits until writes drain. NRI queue submission is serialized against presentation; device-resource access has a separate mutex. Copying this specialized immediate-render path into Lux requires proving its own NRI state and retirement rules.

**Transaction order.** [Observer::EndCurrentEpisode](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Observer.cpp:710) first closes media and waits so delayed encoder/readback failures become visible, combines HadError flags, and only then finalizes numeric/Hub episode data. September hardening unified StopSession with the same open-transaction finalization path. [Parquet worker](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Writers/ParquetDataWriter.cpp:504) closes its current file before writing episode metadata and info.json. This ordering is useful, but no crash-injection/fsync/atomic-directory-rename audit was performed. Do not claim guaranteed power-loss atomicity from it.

**Concrete integrity gap found in source.** [DataRecorder::OnUpdate](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/DataRecorder.cpp:108) calls GetFreeBuffer. If none is available it warns, sleeps 1 ms, and **returns without recording a row**. [Observer::OnUpdateData](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Observer.cpp:398) nevertheless increments CurrentDataFrameIndex and simulation recording time. [GetFreeBuffer](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Writers/ParquetDataWriter.cpp:1356) returns null for an empty three-buffer streaming pool. Thus the comment “stalling physics” is not the actual behavior: only that callback sleeps; the scheduler and row counter can advance without the row. This branch needs a slow-writer/backpressure reproduction; it is a source-supported completeness risk and should not be imported as correct backpressure. A correct no-drop path must wait/retry the same sample, fail the episode, or record a documented gap.

**Determinism is qualified.** Per-camera DLRR is opt-in and metadata marks neural_denoise/bit_reproducible false because results vary with hardware/driver/SDK. Stable callback/column ordering, seeded simulation, and integer timestamps are valuable, but do not make neural temporal processing or platform FP byte identical. The user's removed Lux temporal implementation was poor and is not a present priority; studying recording options does not authorize reintroducing temporal rendering.

**History.** `0c61769ba` introduced threaded data writing in January; `54f5eb05a` added custom schemas; `c6aba6c99f7abf8c08a315ac759894a8ae5979ff` fixed binding/types/schema tests; `3ee455ef1` added sub-frame motion interpolation for offline recording; `097d8bf42...` hardened failure paths. These changes show an evolving product, not a uniformly completed system.

**Lux choice.** The strongest reuse is a test/capture contract: simulation sample ID, render sample ID, frame count, timestamps/units, explicit row schema, terminal corruption state, bounded resources, and close-before-publish. Start with deterministic regression capture/replay for Lux before importing robotics dataset formats, Arrow/Parquet, or the complete recording UI. Force disk/encoder/queue failures and verify no nominally successful output hides missing frames.

## 12. Audio: inspect thread ownership, keep Lux's current backend

Lucky uses MiniAudio/JPL, a dedicated audio thread, source/event management and optional spatial/sound-graph work. [AudioSceneSubsystem](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Audio/AudioScene.cpp:66) collects world-space source positions/parameters into vectors and moves batches to the audio engine, initializes the listener before play-on-awake, and uses a scene-owned concurrent queue for finished one-shot entities that must be destroyed on the game thread. That is a clear ownership/handoff mechanism to compare.

**A valuable failure history.** `79df220e86d6451ce0eef2f3ba53e975c5de15a4` fixes occasional Dist crashes caused by initializing the same audio engine on main and audio threads. The patch removes constructor-side queued initialization, routes Initialize through the audio thread, fences completion before returning, and stops the thread even if initialization failed. The important lesson is one initialization authority and a real completion/lifetime boundary.

**Residual global constraint.** The June desingleton sequence discovers JPL itself still allows only one process engine. `23f76130d` makes Acquire exclusive: later applications can lack audio rather than instantiate a second backend. “Instanceable” wrapper classes do not erase a library singleton. Scene-owned sound state was extracted separately (`a8a1aa8b3`).

**Lux comparison.** Current [AudioEngine](https://github.com/starbounded-dev/LuxEngine/blob/cc25be60385cf342a61030c2b12204c226b94ffa/Core/Source/Lux/Audio/AudioEngine.h#L81) is FMOD Core/Studio with bank/event revisions and invalidation generations; it already handles refcounted bus-lock ownership and manifest-driven runtime banks. Scene updates coordinate Vercidium acoustics, geometry, zones/portals, source/listener state, music/dialogue, and accessibility. A Lucky MiniAudio replacement would discard existing working integration and authored formats without a demonstrated benefit.

**Choice.** Keep FMOD/VA. Compare source-update batching, mixer-thread handoff, play/stop/reload lifecycle, and profiling. Verify bank reload invalidates all wrappers and audio tasks stop before scene resources are destroyed. The available source does not justify claiming Lucky's audio quality or performance is superior.

## 13. Agent, auth, and Hub: reuse boundaries, reject product coupling

**Agent architecture.** LuckyEditor-Agent is a separate library depending on [IEditorAgentHost](M:/LuckyEngine/MAC-Source/LuckyEditor-Agent/include/LuckyEditorAgent/IEditorAgentHost.h:23). Main-thread queries/mutations pass through the host; scene edits go through ExecuteSceneMutation with the relevant scene's undo stack, rejecting absent/inactive/runtime scenes. [ToolRegistry](M:/LuckyEngine/MAC-Source/LuckyEditor-Agent/src/LuckyEditorAgent/LLM/ToolRegistry.h:37) stores schema+handler together, supports typed schema emitters, marks blocking heavy tools for worker dispatch, validates configured path arguments, and caches its advertised schema. Aliases and unknown-tool steering address model mistakes without advertising duplicate names. Hosted streaming clients and local CLI runners are alternative frontends over those tools; their existence does not make edits safe without correct tool/undo/lifetime validation.

**Choice for Lux.** An editor host interface with owner-thread dispatch and undo-aware mutations is directly useful if Lux gains in-editor agent tools or a test harness. Keep tool schema and validation close to the implementation. Require active scene identity at execution time, not just when the background request began. Do not copy Lucky's cloud identity, CLI assumptions, endpoint names, or tool-result privilege/steering policy without designing Lux's own trust boundary.

**Auth/HTTP method.** [AuthService](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Auth/AuthService.h:22) is application-owned, uses OAuth code/PKCE helpers, atomic flow state and mutex-protected token/flow fields, exchange/user-info workers, and a main-thread polled deep-link queue. It includes a manual code path with different state semantics. [HubHttpClient](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Hub/HubHttpClient.cpp:24) centralizes request timeouts, auth headers, JSON headers, SSL setup and one refresh/retry on 401; extra headers strip CR/LF. These are integration methods, not a security audit. Token storage, callback verification, cancellation, concurrent refresh and redirect policies require a separate review if reused.

**Recording is coupled to the product.** [Observer::StartSession](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Observer.cpp:236) requests Hub task approval before starting local recording. [EpisodeReportStreamer](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/EpisodeReportStreamer.h:20) uses a worker, capacity-eight queue, producer backpressure, a 30-second push deadline, stop/drain, and terminal auth/quota/payment/permission statuses that can stop the session. Transient network errors are handled differently. Those are account/billing/product rules, not fundamental rendering or recording requirements. Its timeout fallback can drop a report loudly; do not mistake cloud submission completeness for local media/data integrity.

**Choice.** Keep Lux's local engine functionality independent of LuckyHub approval and robotics accounts. If Lux later needs online features, define a separable service adapter with explicit local failure/offline policy. The reusable pieces are bounded worker queues, typed terminal outcomes, asynchronous UI state, and deterministic local output before optional upload. No connected service or credentials were accessed for this study.

## 15. Sensors: metric depth, approximate masks, LiDAR, and replay

This is a focused follow-up into actual sensor source and selected failure patches. The useful lesson for Lux is the measurement/coordinate/timing contract, not adding robotics dependencies without a product need. No claim about a missing Lux sensor is inferred from an absent filename; current Lux sensor equivalents were not inventoried here.

### Depth and RGBD: specify what each pixel measures

[RecordPackDepth](M:/LuckyEngine/MAC-Source/LuckyEditor/Resources/Shaders/PostProcessing/RecordPackDepth.glsl:7) reads a depth-plane SRV containing reverse-Z [0,1] values. It reconstructs **positive camera-axis eye depth**, using `mul/(add-screenDepth)` for perspective or `mul*screenDepth+add` for orthographic projection. This is axial depth, not Euclidean distance along each pixel ray. It rounds metres/DepthScale and saturates to uint16, packing two adjacent row-major pixels into each uint32 for gray16le output. Default scale 0.001 means millimetre codes with a 65.535 m ceiling; quantization error and saturation are separate from camera near/far limits. Odd pixel counts use a padded final word. Clean depth does not explicitly turn a cleared background depth into a no-return sentinel; its reconstructed far/background value follows the projection/quantization path. Consumers must not silently equate it to the sensor-model zero-invalid contract.

[RecordPackDepthSensor](M:/LuckyEngine/MAC-Source/LuckyEditor/Resources/Shaders/PostProcessing/RecordPackDepthSensor.glsl:109) adds an approximation to a depth camera before quantization: raw-zero background rejection; metric near/max-range gates; incidence from decoded view normals; authored NIR or visible-albedo fallback reflectance; microfacet return/dropout; up to 24 horizontal samples for a one-sided stereo occlusion shadow; and Gaussian noise applied in disparity space (`focalPixels*baselineMetres/z`), quantized to 1/8 pixel, creating roughly z² depth noise. Structured-light mode samples a 2×2-coarser grid. iToF and sparse dToF currently fall through to ActiveStereo, **not distinct completed sensor models**. [DepthSensorModel::All](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/DataTypes.h:454) is explicitly disabled and maps to one ActiveStereo writer because concurrent model writers raced shared render-command resources. An enum is not proof all implementations work.

Transparent surfaces use an auxiliary NIR render target to attenuate the opaque return behind the pane/medium, or report the stronger front glint; this is a screen-space, limited-layer approximation, not calibrated multipath transport. The incidence term uses `abs(nView.z)` rather than the dot product with each off-axis perspective pixel ray, another approximation to check toward image corners. Visible color is only a proxy for 905 nm reflectance when authored data is absent. Noise hashes are seeded per pixel/frame, but shader transcendental/floating-point behavior does not establish cross-GPU byte identity. Diagnostic modes deliberately replace range with internal terms, so diagnostic files must not be consumed as ordinary depth.

**Ownership/cost.** [FFmpeg depth packing](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Writers/FFmpegWriter.cpp:1317) uses the captured recording camera's FOV/projection constants and frame index, GPU packs directly into HOST_READBACK storage, then the existing fence/ring/encoder pipeline writes lossless FFV1 gray16le in Matroska. RGB and depth are separate writers and render work; [CameraRecorder](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/CameraRecorder.cpp:270) waits for **all** RGB/mask/depth backlogs, then issues the same video-frame index to each. This provides a frame-boundary contract, but does not prove physically synchronized multiple real imagers. [gRPC CaptureDepth](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Grpc/GrpcCapturePool.cpp:274) instead uses cached per-view resources plus a one-shot compute command buffer, state restoration, graphics QueueWaitIdle, and a host copy; this blocks GPU work and is not an asynchronous sensor stream.

**History explains two different empty-RGBD failures.** `1179394f2069de531027f07a97769204265eb972` waits for both encoders to close before remuxing; merely queueing CloseFile left half-written inputs. `162fdf7f4ad7b750ea5a402ce30c5022f431d1c0` then replaces shell command invocation with direct ProcessHelper execution because Windows quote stripping broke paths containing spaces. HEAD pairs streams by camera name, not vector position, because DepthOnly cameras change list lengths. RGBD means two already encoded video tracks remuxed with stream copy; it is not a color/depth calibration or registration algorithm. Remux errors are logged and skipped; inspect downstream requirements before promising that an RGBD derivative is part of the same atomic success condition as the base streams.

### Masks: this writer is an approximate target-box generator

[MaskImageWriter::Init](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Writers/MaskImageWriter.cpp:103) specifically caches entities tagged `Red Block` or `Dropbox`, with hardcoded half-extents. [WriteFrame](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Writers/MaskImageWriter.cpp:419) snapshots camera ViewProjection and target positions/extents; a CPU worker [projects eight AABB corners](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Writers/MaskImageWriter.cpp:729), bounds/clamps a screen rectangle, optionally applies deterministic size jitter, and fills it white on a black RGB image. It does not rasterize object triangles, depth-test occlusion, or assign per-instance/class labels. Skipping corners with clip.w≤0 also is not proper near-plane polygon clipping. Lossy H.264/yuv420p output is unsuitable for an exact integer label map. It must not be advertised as a general semantic/instance segmentation ground-truth system merely because its output folder says masks. Other segmentation implementations outside this writer were not exhaustively ruled out.

The worthwhile mechanism is its bounded queued-frame count, contiguous-index validation, immutable frame payload, producer mutex preventing close/frame reordering, terminal failure state, and close-before-temp-file-rename publication. Those correctness methods can transfer independently of the highly specific box-mask algorithm.

### LiDAR: clean collision geometry first, material augmentation separately

[BuildLidarBeamDirs](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/LidarScan.h:16) defines local +X forward and +Z up, with flat index `bin*channels+channel`. Uniform spinning uses azimuth/elevation cells; Livox uses a golden-angle rosette **approximation** whose flat order is emission order, not an elevation channel image. [LidarRecorder::OnUpdate](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/LidarRecorder.cpp:351) selects a slice from RotationHz×dt, transforms it by current body/site pose and mount offset, and calls MuJoCo mj_multiRay for first-hit geometry/normals. MuJoCo coordinates are converted to engine Y-up with the scene axis transform plus root translation for live preview. Recorded normals are rotated back into sensor coordinates, while recorded range is radial metres. Every ray in that tick receives the same episode-relative timestamp and current pose; emission is rounded up and capped at one cycle per callback. This is not per-beam continuous-time motion distortion or exact pulse scheduling across arbitrary dt/rotation rates.

**Optimization and tradeoff.** Beam/ray/normal/ID scratch arrays are reused, and mj_multiRay amortizes broad-phase traversal over the scan. Mount/robot self-ignore and geometry-group filters avoid unwanted hits. Optional pass-through/reflection geometry needs extra mj_ray traversals, so a per-model/per-geom material mask restricts secondary casts to surfaces that can use them; stepped continuation is bounded. Extra secondary distances/normals are columns attached to the primary ray, not new primary rows that replay would mistakenly augment again. Data remains a clean collision scan; material noise/returns are evaluated for preview or exported variants.

[LidarParquetWriter](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Writers/LidarParquetWriter.cpp:194) writes timestamp, bin/channel, radial range, geom ID, hit flag and sensor-frame normals, with -1 range on miss and optional secondary columns. It wraps reusable vectors into Arrow arrays and flushes 16,384-row groups using ZSTD level 1, Snappy, or uncompressed fallback. **This writer flushes from the caller path; it is not the DataRecorder background writer.** Synchronous disk/compression and optional FFmpeg proxy writes can therefore cost simulation time. [CloseFile](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Data/Writers/LidarParquetWriter.cpp:564) closes before promoting `.parquet.tmp`, removes corrupt temporary output and orphan sidecars/proxies, and marks failures. This is a useful publication boundary, not proof of fsync/power-loss atomicity across the whole file trio. The colored proxy is only a visualization; `5828885951c13a9d5d81315f6811e9e5f6e3c953` fixed a Livox emission-index array being treated as spatial image axes and introduced real azimuth/elevation projection plus viewable size bounds.

### Replay/material bridge: identity and calibration are separate from geometry

[LidarReplayPanel](M:/LuckyEngine/MAC-Source/LuckyEditor/src/Panels/LidarReplayPanel.cpp:1251) loads and sorts episode rays, rebuilds the same beam table, bounds a playhead window with binary searches, and caps displayed points. It loads a pose timeline from recorded state and [samples nearest-earlier pose](M:/LuckyEngine/MAC-Source/LuckyEditor/src/Panels/LidarReplayPanel.cpp:1641), not interpolated motion. Pose reconstruction is explicitly a single-body MVP using the first free joint, with live body/site transforms as fallback. It does not guarantee arbitrary moving multi-body sensor rigs replay exactly. `8190a26e657f13058a675cfae5a444f75ae6fea2` fixes cross-episode pose bleed by filtering the global episode_index column instead of chunk-local filenames, and changes pose selection to upper_bound/previous. This is an identity/time lookup failure, not a raycast error.

[MaterialVoxelBake](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Lidar/MaterialVoxelBake.cpp:298) bridges collision geom hits to visual NIR materials by surface-sampling visual triangles at ≤half-cell spacing, storing textured reflectance/roughness/metalness/continuation data in a dense position-keyed voxel grid. The max-axis dimension grows effective cell size to bound memory; direct samples outrank dilated splats, ties overwrite. A geom-material table is preferred for recorded secondary hits where cell quantization would confuse shallow water with the bottom, but must be suppressed when recording and edit-time MuJoCo ID spaces differ. Material fingerprints and saved build parameters/version detect some stale bakes; transforms are deliberately excluded, so this is not full moving-scene identity/coverage validation. Dense memory, bake cost, thin surfaces, overlap, quantization and mismatched visual/collision shapes remain limitations.

[LidarReturnModel](M:/LuckyEngine/MAC-Source/Hazel/src/Hazel/Lidar/LidarReturnModel.h:23) combines reflectivity/range attenuation, microfacet incidence, dropout, range noise, transmission/reflection continuations and echo limits. Replay export snapshots parameters, seeds variants, processes batches across frames, reports losses by cause, and writes model/bake/provenance metadata. These are motivated approximations with a calibration interface; inline citations and manufacturer preset names do not establish sensor validation. Bake misses preserve geometry with explicit unknown-material sentinels instead of silently changing the point distribution.

**Lux decision/validation.** Reuse explicit unit/basis/projection contracts, common capture/replay beam definitions, owned snapshots, immutable augmentation inputs, terminal failures, and truthful distinction between clean geometry and sensor artifacts. Avoid importing the robotics stack solely for these lessons. A focused test set is a metric plane at the image center/corners under perspective and orthographic projection; far/no-hit/saturation and odd image dimensions; glass/occlusion edge cases; frame pairing with DepthOnly and spaced paths; mask occlusion/near-plane cases; spinning/rosette counts across tick rates; translated/rotated mounts; missing self-hit geometry; and replay across chunk/episode boundaries. No such capture, hardware calibration, output decode, or replay was executed here.
