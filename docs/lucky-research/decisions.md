## Decisions for Lux and verification

The following is a recommendation for choosing focused work, **not an approved engine-change list**. Priority reflects a concrete correctness/quality opportunity or the user's interest in documentation. Features that already exist in Lux are compared by method. A useful next implementation should remain small enough to isolate its benefit and failure modes.

| Candidate | Choice | Reason and boundary | Evidence needed to accept a Lux change |
|---|---|---|---|
| Editor-integrated learning/documentation | **Adapt the method; high product value** | Context-specific guide/API links, version ownership and discoverable help reduce learning friction. Start from Lux's existing editor guides; add packaged offline content rather than requiring a website or account. | Relocated install; offline lookup; valid inspector/settings links; compiled runnable tutorial; Help content and ScriptCore versions agree. |
| Imported source-node placements | **Focused correctness candidate** | Lucky retains all node placements for a shared submesh; current Lux overwrites one submesh transform and publishes one corresponding row. Preserve Lux's retained rendering while representing every placement. | One geometry object referenced by multiple transformed nodes; correct bounds, picking, shadows, collision policy, runtime load and reload. |
| Attribute-aware LODs and meshlet building | **Strong comparative prototype** | Lucky's meshoptimizer topology/normal/border-aware pipeline targets visual and cache error directly; Lux's position-grid averaging/input-order meshlets make different compromises. | Textured seams, hard edges, thin/two-sided geometry, rigged exclusions; equal visual quality; import time, bytes, triangle counts, CPU/GPU cost and error bounds. |
| Render-command arena | **Focused robustness candidate** | Current Lux still has unchecked fixed capacity. Lucky adds accounting and failure checks, but its alignment/publication/failure policy is not a complete safe design to copy. | Exhaustion in release builds; over-aligned callables; construction/publication ordering; queue swap/shutdown; no partial rendering silently accepted. |
| 2D descriptor limits and font caches | **Fix shared weaknesses; copying Lucky is insufficient** | Both inspected implementations have unchecked 32-slot sprite/font registration and weak name/em-only font cache validation. Lux already fixes a quad chunk rollover that Lucky still lacks. | 31/32 distinct nonwhite textures, 32/33 atlases, 5,000/5,001 quads, mixed transparent ordering, corrupt/changed/same-named fonts, in-flight descriptor snapshots. |
| Shader reflection and descriptor identity | **Audit, then adapt only the actual gap** | Lucky fixed cross-shader name pollution and nondeterministic binding-to-range mapping. Lux deliberately has a shared binding namespace; verify its invariants before changing it. | Compile shaders in reversed order; legal repeated binding numbers with different names; native range contents; hot reload and shared bindless pipeline compatibility. |
| Exact GPU generation ownership | **Audit existing Lux lifetime path** | Retaining a mutable CPU asset is not enough if queued work uses an earlier native image/buffer/BLAS. Lux already has generations and completion-based ownership; inspect rather than duplicate. | Reload/delete/resize with frames in flight; descriptor slot pressure; aborted submission; native resources survive exactly until consumers complete. |
| GPU profiling controls | **Extend existing Lux tools** | Content-ready warmup, accepted samples, overflow/failure flags and raw HDR A/B comparison are useful; Lux already has golden/performance capture and Tracy. Lucky's tile-GPU timestamp lessons prevent measuring instrumentation overhead as an optimization. | Automated A-B-A with same scene/camera/device/config; frame vs pass timing perturbation; variance/readiness metadata; image parity. |
| Retained scene, subresource states, static shadow caches | **Keep Lux's approach while measuring it** | Lucky's per-frame gather and whole-image state model do not establish an improvement. Lux's bookkeeping/invalidation still needs tests and can cost CPU/barriers. | Edit/reload invalidation, unchanged-scene CPU cost, resting-state barrier counts, moving-to-static caster transitions, offscreen shadow correctness. |
| Split lighting / compact G-buffer / octahedral point shadows | **Hardware- and bottleneck-dependent experiments** | Lower register pressure or memory use may help, but add bandwidth/decode/seam/maintenance costs. Lucky split lighting remains default-off; reported M2 results were not reproduced. | Occupancy/bandwidth and frame time on target hardware; raw HDR difference; point-shadow seams/contact quality; reference path retained. |
| Geometry preprocessing cache | **Adapt validation; improve dependency key and publication** | Lucky validates complete sections before publishing, but source-stat keys and cleanup do not cover every dependency/invalidation case. | Corrupt/truncated/oversized entries; external `.bin` change; processor/settings revision; interrupted write; live object unchanged on failed load. |
| Prefab structural reconciliation | **Goal-driven extension** | Lucky's child/source identity matching addresses edits Lux's current value propagation does not fully cover. Lux variants are a separate existing strength. | Nested ownership, instance-added/deleted/reparented children, overrides, entity references, cycles, runtime dependency closure. |
| Graph authoring and material previews | **Adapt architecture when the workflow is needed** | Shared canvas with domain compilers and last-good prototype publication is reusable; thumbnail budgets bound per-frame work. Prototype cache freshness and preview blocking remain concerns. Newer public procedural tooling is absent from this source pin. | Invalid/cyclic edits retain last good output; schema/cache changes, same-stem assets, undo, preview failure/retry and project switching. |
| Undo, export, audio | **Preserve current Lux foundations** | Scoped value diffs, export guards/sequencing, and FMOD/VA already solve important problems. Borrow exact reversal, common manifests and owner-thread batching where useful. | Repeated hierarchy undo without drift; active-job shutdown; relocated runtime; bank/asset reload; stable scene/audio lifetime. |
| Process host/project services and optional modules | **Adopt when isolation/capabilities require it** | Lucky makes boundaries explicit, but still has process-global constraints and shutdown contracts. Do not refactor every singleton without a concrete use case. | Multiple fixtures/projects, partial startup failure, capability fallback, repeated teardown, workers and GPU drains before owner destruction. |
| Fixed-step scripting/simulation authority | **Specify gameplay ordering first** | Lucky's serial integer-ns five-phase scheduler is tailored to multirate robotics. Lux needs correct script/controller/physics order before it needs all 256 callback masks. | 30/60/144 display Hz, pause/single-step, force application, root motion, replay seed and defined hitch policy. |
| Weak references | **Improve the contract, independently design the algorithm** | Lux's live-address check does not pin lifetime. Lucky's separate block and Lock API are instructive, but the strong counter still lives in the object and the release/lock interleaving remains unresolved here. | Concurrent last-release/lock stress with sanitizers and forced address reuse; invariant proof, not only a sequential test. |
| Recording / remote tools / crash watchdog | **Selective tooling opportunities** | Sample IDs, immutable owner-thread snapshots, terminal failure states, close-before-publish and out-of-process observation are transferable. Lucky's recording/backpressure and detached-worker compromises need correction before reuse. | Slow writer/disk/encoder failure; no hidden row/frame gaps; concurrent requests, cancellation and stale-scene rejection; deliberate hang/crash/normal exit. |
| Animation and path tracing | **Future goal-dependent studies** | Useful compressed-sampling/root-motion and reference-renderer methods exist. This review does not establish a fully equivalent current Lux animation pipeline or justify a large port. | First establish current Lux behavior; then an end-to-end small path with reload, error/performance and ownership validation. |
| Temporal reconstruction / DLSS / NRD | **Document only; deferred priority** | Semantic identity, accepted-frame transactions, previous deformation and reset taxonomy explain past failures. Presence in Lucky is not a reason to reintroduce it now. | If revisited later: explicit motion/depth/jitter/color contracts, reset reasons, failed-frame rollback, disocclusion/deformation tests and stable reference comparisons. |
| MuJoCo, learning policies, robotics datasets, accounts/Hub, browser simulation | **Retain as specialized references** | Excellent problem-specific methods; no demonstrated need to turn Lux into Lucky's robotics product. The WASM target is a small MuJoCo simulator, not native-game web export. | A concrete Lux product goal and a separately bounded design before adopting the dependency/UI/service stack. |

### A practical first sequence

First make two narrow changes reviewable on their own: a bounded render-command submission design, and a shared-node import fixture that demonstrates all placements reaching the retained renderer. In parallel, define the Lux documentation topic map from the existing guides and one complete tutorial; this is independent of renderer changes and directly addresses the user's interest.

Next compare the geometry-processing methods using identical input assets and visual-quality targets. Audit descriptor identity/hot reload and generation ownership while extending the current capture tooling with explicit readiness/failure metadata. Only after those measurements should larger rendering or lifecycle reorganizations be chosen. This is an order for future decisions, not work implemented by this research request.

## Coverage limits and research artifacts

This report consolidates source/history investigations across rendering, content/editor/documentation, runtime/simulation, reflection/crash/services, and the browser target. It indexes the complete reachable Lucky history and tracked tree and uses the already completed Lux history review. **Indexing every entry does not mean every line or diff was deeply audited.** Focused call chains and repairs are described with source anchors; chapter-specific blind spots remain explicit.

Unresolved questions include current private Hazel behavior beyond the available baseline; details inside unavailable submodules; the public manual's generator/deployment implementation; actual GPU performance and visual quality; every asset-format/prefab/runtime compatibility edge; and source-level failure concerns awaiting reproduction. Neither current online documentation nor a test file's presence certifies the supplied development snapshot.
